## Aldenexia: Lightfall — Game Flow & System Reference
## Last updated: 2026-09-19
## Purpose: Running reference for how all systems connect, for troubleshooting and onboarding.

================================================================================
AUTOLOADS (Global Singletons — always in memory, any scene can access them)
================================================================================

Global       → Scripts/global.gd
  - Holds all live player state in Global.player_data (Dict)
  - Also holds Global.current_character_data, current_character_name
  - Loads xp_table.json and character_options.json at startup
  - Game time system: 10-month, 36-day/month, 6-day/week calendar; 30 real
    seconds = 1 game minute
  - save_player_data_to_file()  → user://saves/{name}_character_stats.json
  - load_player_data_from_file() → reads save, calls set_player_data()
  - grant_currency(field, amount) → adds copper/silver/gold/platinum
  - Signals: chat_state_changed, time_changed, day_changed, month_changed,
    currency_changed

GameLog      → Scripts/game_log.gd
  - Pure signal bus, no state.
  - GameLog.log_general(text) → emits general_message
  - GameLog.log_combat(text)  → emits combat_message
  - GameLog.set_autoattack(bool) → emits autoattack_changed
  - game_log_window.gd connects to all three and routes them to the correct tab.

Inventory    → Scripts/inventory_autoload.gd
  - basic_inventory[12] — character sheet carry slots (bags or items)
  - bag_contents["0"…"11"] — contents of each bag in the above slots
  - equipped{slot → item_dict or null} — 25 paperdoll equipment slots
  - Loads all item definitions from items.json on startup
  - equip_item() / unequip_item() — emits equipment_changed when slot changes
  - sync_to_global() — writes inventory_data back into Global.player_data
  - Signals: inventory_changed, equipment_changed

GlobalBackgroundMusic → Scenes/global_background_music.tscn
  - AudioStreamPlayer that auto-starts on main_menu and character_creation, plus any
    scene listed in its SCENE_MUSIC table (Lumora Outskirts -> Sands of Lumora.ogg).
    Stops automatically for any other scene.
  - COMBAT MUSIC (added 2026-09-19): while the LOCAL player is fighting in a scene
    that has zone music, the zone track crossfades out (1.5s, and is PAUSED so it
    resumes from the same spot) and "Tomb of the Lost.ogg" (looped at runtime — its
    import setting is loop=false) crossfades in. It goes back 8s after the last blow
    dealt or taken, again with a 1.5s crossfade. Constants: COMBAT_TRACK/FADE/LINGER.
    "Fighting" = CombatNode.seconds_since_engaged() on the local player, polled 4x/sec.
    That clock (last_engaged_msec, mark_engaged()) is stamped in CombatNode's
    resolve_attack() (attacker AND target, even on a miss), take_damage() (amount>0)
    and generate_threat() (damage_dealt>0 only — pure healing does not count), which
    together cover melee, spells/cone/pbaoe, pets and anything that hits you. It is
    deliberately separate from CombatNode.in_combat, which nothing ever sets (turning
    it on would also change decay_threat()). Menu scenes and non-zone scenes never
    play combat music; leaving a zone scene mid-fight ends it.

SCENE FLOW (How the player moves between screens)
================================================================================

  main_menu.tscn
      │
      ├─ [New Character] → character_creation.tscn
      │       └─ [Begin] → saves {name}_character_stats.json
      │                  → Global.load_player_data_from_file()
      │                  → lumora_outskirts3d.tscn
      │
      └─ [Load Game] → instantiates load_game.tscn as overlay
              └─ [Load] → Global.set_player_data(parsed_json)
                        → lumora_outskirts3d.tscn (active 3D zone)

  lumora_outskirts3d.tscn (main gameplay)
      └─ [Escape → Save & Exit] → saves file, frees all CanvasLayer UI,
                                   returns to main_menu

LUMORA OUTSKIRTS 3D — WHAT LIVES IN THE SCENE
================================================================================

lumora_outskirts3d.tscn contains:
  - DirectionalLight3D + WorldEnvironment (procedurally generated sky —
    Background = Sky, ProceduralSkyMaterial)
  - CharacterBody3D (player3d.tscn) — the playable character
  - NavigationRegion3D, containing:
      - LumoraOutskirts — instanced res://zones/LumoraOutskirts.glb (the Blender
        level art: walls, floor, docks, camps, POI markers, etc.)
      - LumoraOutskirts_Collision — StaticBody3D with one trimesh
        CollisionShape3D per mesh in the .glb (14 as of 2026-08-23), regenerated
        via a headless Godot script any time the .glb is re-exported from
        Blender (see "3D LEVEL COLLISION PIPELINE" below). NOT auto-generated
        by Godot's importer — must be re-run manually after every Blender export.
  - monster_template instance (test skeleton spawn) + MobSpawner3D
  - campfire (Scenes/campfire.tscn) — Campfire.glb + flame/smoke GPUParticles3D +
    looping AudioStreamPlayer3D (max_distance=10.0) + WarmthArea (Area3D,
    SphereShape3D radius 4.0). campfire.gd logs "The warmth of the fire renews
    your spirit as you take shelter nearby." to the General tab once when the
    player (group "player") enters the area; resets on exit so it can fire
    again next visit. As of 2026-09-13, also starts a 30s Timer on entry
    (cancelled on early exit — WARMTH_LINGER_SECONDS) that, on completion,
    grants "campfire_warmth" via combat_node.apply_effect(..., 300.0,
    {hp_regen_bonus:2, mana_regen_bonus:2, stamina_regen_bonus:2}) — same
    active_effects system as stances, shows up on the buff bar automatically.
    player3d.gd's HP/mana regen tick and stamina's continuous regen both now
    add combat_node.get_modifier("*_regen_bonus") alongside their existing
    math.
  - "Archery Targets" (3 instances) and "Bone Spears" (4 instances), added
    2026-08-25 — purely decorative set-dressing (res://models/Archery
    Target.glb, res://models/Bone Spear.glb), no script attached, same
    grouping convention as Campfires above.

Note: the Terrain3D addon is present in addons/ but is NOT used by the current
zone — the level is entirely the Blender-authored LumoraOutskirts.glb mesh.
lumora_outskirts.tscn (2D) is legacy and not the active gameplay scene.

3D LEVEL COLLISION PIPELINE (must be re-run after every Blender re-export)
--------------------------------------------------------------------------------

Godot's glTF importer does NOT auto-generate physics collision from an
imported .glb unless mesh objects are named with a "-col"/"-colonly" suffix
convention in Blender (not currently used in this project). Collision for
LumoraOutskirts_Collision is instead generated by a saved headless Godot
script — as of 2026-08-23 this is no longer a one-off; run:

  ./tools/regen_lumora_collision.sh

from the project root after every Blender re-export. It does both steps
below in one command and exits non-zero with a warning if it detects the
degenerate-transform gotcha. To run the steps individually (or if you need
to tweak the generation logic, see tools/regen_lumora_collision.gd):
  1. Load res://zones/LumoraOutskirts.glb standalone, walk every MeshInstance3D
     (skipping any with visible=false or no mesh resource).
  2. For each: mesh.create_trimesh_shape() (local-space vertex data) + a
     manually-computed global transform (walk the parent chain multiplying
     Node3D.transform — NOT Node3D.global_transform, which returns identity/
     errors on a node that was never added to a live SceneTree). Text-splice
     the generated sub_resource + node blocks directly into
     Scenes/lumora_outskirts3d.tscn (NOT a full PackedScene.pack()+save() —
     that was tried first and silently stripped ext_resource UIDs and failed to
     persist edits inside the instanced LumoraOutskirts sub-scene at all).
     Command: `godot --headless --path . --script res://tools/regen_lumora_collision.gd`
  3. Run `godot --headless --path . res://Scenes/lumora_outskirts3d.tscn
     --quit-after 60` and grep stderr for "det == 0" / "cannot be normalized" —
     both indicate a singular (non-invertible) transform on some mesh, which
     will corrupt player physics silently (see gotcha below).

Shape naming matches each mesh object's name in Blender (spaces preserved,
"_shape" suffix appended) — e.g. new objects "Bone Spear", "Mausoleum",
"Small Crypt 1/2" added 2026-08-23 produced "Bone Spear_shape",
"Mausoleum_shape", etc. with no manual mapping needed.

GOTCHA — hand-edited/patched geometry can get inverted normals, making
collision one-sided (2026-08-23, Mausoleum doorway):
  ConcavePolygonShape3D collision is one-sided by default
  (backface_collision = false) — it only registers a hit on the side the
  triangle's face normal points toward. This is invisible in the Blender
  viewport (backface culling off by default) and doesn't throw any import/
  physics error, so it silently produces direction-dependent collision:
  solid from one approach angle, walk-through from the other, and confusing
  "can't enter, but there's clearly an opening" symptoms if only some faces
  of a patched area are affected. Diagnosed by direct PhysicsServer3D
  raycasts against the live scene (both approach directions) rather than by
  inspecting the mesh — the mesh data alone looked fine. Most likely to hit
  new geometry that was manually patched into a hole (e.g. filling a deleted
  cube face with a new hand-built wall-with-doorway), since Blender's normal
  direction for newly created faces isn't automatically consistent with the
  surrounding mesh.
  FIX (applied at the pipeline level, not per-asset): tools/regen_lumora_collision.gd
  now sets `backface_collision = true` on every generated ConcavePolygonShape3D,
  so collision is two-sided regardless of Blender normal direction. No manual
  normal-recalculation needed per object going forward.

GOTCHA — degenerate Blender scale on any axis breaks physics silently:
  If a Blender object has a 0 scale on any axis (common accidental result of
  flattening a mesh via scale instead of editing vertices — invisible in
  Blender if the mesh's local geometry already lies flat on that axis), the
  resulting transform matrix is singular. Godot's physics engine throws
  "Condition det == 0" trying to invert it and produces NaN contact normals
  every physics tick the player touches that shape — symptoms are a frozen
  character, a broken-looking camera, and rendering that looks wrong (all
  downstream of the corrupted CharacterBody3D transform, not real bugs in
  those systems). Remember Blender is Z-up; glTF/Godot are Y-up, so Blender's
  Z-axis scale/location maps to Godot's Y-axis — check the right field.

LOCAL LIGHT SOURCES (campfire.tscn, torch.tscn) (2026-08-23)
================================================================================

GOTCHA — OmniLight3D.light_projector is broken under this project's
renderer, don't use it: project.godot sets
rendering/renderer/rendering_method = "mobile" (Forward Mobile). Both
campfire.tscn and torch.tscn originally had an OmniLight3D with
light_projector set to a small radial GradientTexture1D (presumably meant
to fake a soft warm falloff/vignette). Under Forward Mobile this doesn't
render as a falloff at all — it produced a hard-edged, wrong-colored
triangular wedge across the ground instead of normal soft omnidirectional
light (confirmed visually: screenshotted the live scene in-engine — not
the --headless dummy renderer, which renders nothing — with and without
the projector; removing it produced the expected smooth warm glow).
Fixed by deleting light_projector (and the now-unused
Gradient/GradientTexture1D sub_resources) from both OmniLight3D nodes.
Both are otherwise identical hand-built structures: OmniLight3D +
unshaded/alpha-blended QuadMesh GPUParticles3D (flame + smoke, borrowed
fire/smoke textures from Assets/), shading_mode=0 so particles render
unaffected by scene lighting/ambient. If you add more torches/braziers/
lanterns, copy this pattern minus light_projector. omni_range isn't set
explicitly on torch.tscn's light (class default 5.0) vs campfire.tscn's
explicit 8.0 — the wall right next to a torch can still look mostly dark
even when correctly lit, because dark stone has much lower albedo than the
sandy ground campfires usually sit on; that's the material, not a bug.

To debug "can't see X" visual complaints like this one going forward: get a
REAL screenshot via `godot --path . --script <script>` (NOT --headless,
which uses the Dummy rendering driver and renders nothing useful) — spawn
a temporary Camera3D, position/look_at it manually, wait ~60-90
process_frames for particles/lighting to settle, then
get_root().get_texture().get_image().save_png(path). A real X11 display
was available in this environment (checked $DISPLAY) — confirm that's
still true before assuming this approach works.

TIME SYSTEM & DAY/NIGHT CYCLE (2026-08-23)
================================================================================

Global.gd is the single source of truth for the in-game clock. Runs at
REAL_SECONDS_PER_GAME_MINUTE = 1.0 (1 real second = 1 game minute), a
standard 24-hour day (HOURS_PER_DAY = 24). DAY_START_HOUR=6, DAY_END_HOUR=21
(day 06:00-21:00, night 21:00-06:00) — at the 1:1 rate that's 15 real
minutes of day, 9 of night. is_daytime() uses these same constants.
game_time.hour/minute/day/etc. advance via advance_game_time(), called from
_process() once REAL_SECONDS_PER_GAME_MINUTE of real time accumulates;
emits the `time_changed` signal every game-minute tick.

Scripts/day_night_cycle.gd (per-zone Node, e.g. "DayNightCycle" in
lumora_outskirts3d.tscn) drives the sun (DirectionalLight3D) and sky/ambient
(WorldEnvironment/ProceduralSkyMaterial) for outdoor zones. It does NOT run
its own timer — it listens to Global.time_changed and derives phase
(DAY/NIGHT) + progress (0..1 through the current phase) purely from
Global.game_time, so the sky and the calendar can never drift apart. Dawn/
dusk is a smooth visual blend (dawn_dusk_fraction, default ~0.0667 = ~1
in-game hour) inside the start/end of the DAY phase, not a separate
calendar phase — night sun is repurposed as dim, cool "moonlight" so local
light sources (campfire, torches) are the dominant light at night by
design. Exported vars control all colors/angles/energies from the
Inspector. TUNED 2026-09-13: moon_energy was 0.04 (~3% of daytime's peak
1.3) and night_ambient_energy was 0.05 (~5% of daytime's 1.0) — reported as
"pitch black, impossible to see anything," which it genuinely was. Raised
to 0.25 and 0.18 — still a clearly dim, moody night (local light sources
are still the dominant light by design, per above), just no longer
functionally lightless. If still too dark in practice, these two exported
vars are the next thing to nudge; a carryable player torch was discussed as
a follow-up but not built this session.
FIXED 2026-09-14 (Session 42): _apply_lighting() animated sky_top_color and
sky_horizon_color every tick but never touched ground_horizon_color (the
sky dome's lower hemisphere), which sat at its bright default around the
clock — invisible by day, but at night the sky above went dark while the
ground half of the horizon stayed lit, producing a glowing horizontal seam
right at the horizon in every outdoor zone. Fix: ground_horizon_color now
mirrors the same computed sky_horizon_color every update. Verified via a
headless test forcing 2 AM game time and reading both values back off the
live ProceduralSkyMaterial — confirmed exact match.
Emits phase_changed(is_day) — currently unused but available
(e.g. for auto-lighting torches at dusk later). Adds itself to group
"day_night_cycle" in _ready() — look it up via
get_tree().get_nodes_in_group("day_night_cycle"), NOT
get_tree().current_scene.get_node(...); current_scene is not reliably the
zone root here (confirmed: it was null in a manual-instantiate headless
test, and this codebase's established pattern for any other-node lookup
is groups anyway — see player/npc groups below).

To add day/night to another outdoor zone: add a Node child named
"DayNightCycle" with day_night_cycle.gd attached, siblings named
"DirectionalLight3D" and "WorldEnvironment" (or repoint sun_path/
world_environment_path). Indoor/dungeon zones can skip it entirely —
nothing else currently depends on it.

/time chat command: Scripts/game_log_window.gd, in the "/location" match
block inside _handle_slash_command() (renamed from the old literal "/loc"
2026-09-14 Session 42 — see prefix-matching note below). Prints
Global.format_full_date(), the DayNightCycle node's day/night status + time
to next phase (group lookup, null-safe — skips that line in zones with no
DayNightCycle), and real-world time.

GOTCHA — Scripts/chat_window.gd + Scenes/chat_window.tscn are DEAD 2D-era
code (2026-08-23): they're only instanced inside Scenes/main.tscn, a
leftover 2D scene (Node2D root, CharacterBody2D player, player.gd/npc.gd)
that nothing loads anymore (no script references "main.tscn" at all — grep
confirmed zero hits). It also isn't a general console even where it did
run — chat_input.visible=false by default, only shown when an NPC's
`hailed` signal fires. The REAL always-on 3D chat/log window is
Scripts/game_log_window.gd (CanvasLayer, in player3d.gd's _spawn_hud()
list) — General/Combat tabs fed by the GameLog signal bus, PLUS its own
chat_input LineEdit and _handle_slash_command() dispatcher (currently
"/location", "/time", "/hail", "/appraise", "/follow" — full behavior of
each in change_log.txt's "Chat Commands" reference at the top of the
file). The two files have near-identical _handle_slash_command() structure
because game_log_window.gd is a 3D port of chat_window.gd's dispatcher that
nobody deleted the original for. Don't add new slash commands to
chat_window.gd — verify a script is actually reachable from
lumora_outskirts3d.tscn (or wherever the live zone is) before assuming it's
live, the same way this file's "2D→3D migration complete" line already
warns for Scripts/skeleton.gd et al.

Commands are Linux-shell-style prefix-matched (added 2026-09-14, Session
42): _resolve_command(typed) checks the COMMANDS const array for an exact
match first, then any command the typed text is an unambiguous prefix of
(e.g. "/fol" -> "/follow", "/loc" -> "/location" — this is why "/loc" was
renamed from being the literal command name to just an abbreviation of it).
Zero matches logs "Unknown command"; more than one logs "Ambiguous command"
with the candidate list rather than guessing. _handle_slash_command() calls
this once up front and matches on the resolved canonical name, so each
individual command's match-arm code is unaffected by the abbreviation
logic. Adding a new command = add its canonical "/name" to COMMANDS and a
match arm — abbreviation support is automatic, nothing per-command needed.

Nothing else in the codebase depended on the old calendar pacing before
this change (REAL_SECONDS_PER_GAME_HOUR/_DAY were dead constants,
is_daytime() and the time_changed/day_changed/month_changed signals had
zero callers) — confirmed by search before changing the rate, so this was
low-risk.

PLAYER SYSTEM (player3d.gd)
================================================================================

Class: Player3D extends CharacterBody3D
Group: "player"
Scene: Scenes/player3d.tscn (contains CameraRig → CameraController + Camera3D)

--- _ready() order ---
1. add_to_group("player")
2. Instantiate CombatNode and add as child
3. Connect Inventory.equipment_changed → _on_equipment_changed()
4. load_faction_standing()       — reads Data/player_faction.json
5. _load_spell_cache()           — reads Data/player_spells.json +
                                   Data/player_skills.json into Dicts
6. load_player_data_from_global()— reads Global.player_data, loads inventory,
                                   applies equipment to CombatNode
7. _spawn_hud()                  — instantiates five HUD scenes on scene root,
                                   tags them "game_hud" (player_frame,
                                   target_frame, game_log_window, action_bar,
                                   stance_bar — added 2026-08-25)

--- Movement ---
  WASD / Arrow keys: move_forward, move_backward, strafe_left, strafe_right,
                     turn_left, turn_right
  Shift (toggle_run): toggles run/walk
  R (toggle_autorun): keeps moving forward until toggled again or move_backward
                     is pressed. Logs "Autorun enabled/disabled." to General tab.
  Ctrl (crouch): crouches
  Space (jump): costs stamina
  X (sit): toggles sitting (no movement, faster stamina regen; logs message)
  Stamina: sitting 20/s (fastest) > standing idle 10/s > walking 5/s (added
  2026-08-23 — walking previously neither drained nor regenerated) > running
  drains 10/s.
  Movement/jump/crouch/run-toggle/combat input is suppressed while any
  LineEdit has focus (chat box open) — checked via
  get_viewport().gui_get_focus_owner() is LineEdit in _physics_process, added
  once the chat box became usable while walking around, not just static NPC
  dialogue. Velocity decelerates smoothly to a stop instead of going stale.

--- Camera (camera_controller.gd) ---
  Child Node3D "CameraRig" on Player3D.
  TWO distinct look modes as of 2026-09-13, both write the same shared
  rotation_x/rotation_y state on the CameraRig (so switching between them
  mid-session can jerk back within whichever cap applies next time the mouse
  moves — acceptable, rare edge case, not smoothed):
    F12 (Global.mouselook_enabled, single source of truth — see MOUSE MODE
    below) → free-look. Uncapped yaw (wrapf(-PI,PI), never grows unbounded,
    can spin all the way around); pitch capped to ±89° (FREE_LOOK_MAX_PITCH)
    only to avoid flipping past straight up/down. Previously (until
    2026-09-13) this reused the ±90°/±45° "head turn" clamp below, which
    made it impossible to even look directly behind you.
    Hold Right Mouse Button (independent of F12; mouselook takes priority
    and owns the mouse mode if already on) → "head turn". Capped to
    MAX_YAW=±90° (180° total)/MAX_PITCH=±45° (90° total) — a realistic
    head-turn range, holds at the cap instead of wrapping, no snap-back on
    release. Hides the mouse (Input.set_mouse_mode HIDDEN, changed from
    CAPTURED 2026-09-14 Session 42 — CAPTURED locks the OS cursor to the
    window center every frame to report unlimited relative motion, which
    head-turn's ±90°/±45° cap never needed, and made the literal cursor jump
    to screen center on release of EVERY right-click, including a quick
    click to loot/shop that never dragged at all; HIDDEN reports real
    relative motion without touching cursor position) only while held;
    calls Global.restore_mouse_mode() on release.
  Mouse wheel → zoom (MIN_ZOOM=2m–MAX_ZOOM=12m). As of 2026-09-14 (Session
  30), zooming all the way in (current_zoom hits MIN_ZOOM) from EITHER
  third-person mode auto-switches current_mode to FIRST_PERSON instead of
  just stopping at the closest third-person distance; scrolling back out
  while in FIRST_PERSON pops back to THIRD_PERSON_BEHIND at MIN_ZOOM — one
  continuous zoom gesture rather than a jump between unrelated modes.
  Home key → cycle three modes (unaffected by the above, still a direct jump):
    THIRD_PERSON_BEHIND (default, 6m back)
    THIRD_PERSON_ANGLED (tactical, 8m back / 5m up / 45°)
    FIRST_PERSON (eye level)
  Invert Look Y (added 2026-09-14, Options menu — see below): a single
  shared setting (Global.settings["invert_look_y"]) flips the vertical sign
  in BOTH _handle_free_look() and _handle_head_turn() — not two separate
  toggles, one control affects both look modes.

--- Mouse mode (Global.gd, added 2026-09-13) ---
  Global.mouselook_enabled (bool, default false) is the single source of
  truth for "should the cursor be captured by default" — camera_controller.gd
  (F12) is the only thing that writes it. Global.restore_mouse_mode() sets
  CAPTURED if mouselook_enabled else VISIBLE. Every UI window (pause menu,
  character sheet, backpack, corpse loot window) still forces VISIBLE
  unconditionally the moment it opens (so its UI is always clickable
  regardless of mouselook state), but all now call restore_mouse_mode() on
  close instead of hardcoding a mode — fixes two real bugs: the loot window
  used to force CAPTURED on close even with mouselook off (mouse stuck
  hidden after looting), and every other window forced VISIBLE on close
  even with mouselook on (silently cancelled mouselook).

--- Targeting ---
  Tab          → tab_cycle_target() — sorts live monsters by distance, always
                 selects index 0 (nearest). Logs "Target: [name] — HP x/y (zm away)".
                 (Fixed 2026-08-23: "tab_target" and "target_closest" input
                 actions had their key bindings swapped — tab_target was on
                 Escape, target_closest [unused elsewhere] was on Tab. Swapped
                 back in project.godot; Escape is now only the pause menu again.)
  Ctrl+Tab     → "target_closest" action — bound but not yet wired to any
                 function (known gap). Landed on Ctrl+Tab after Escape (from
                 the swap fix) and Shift+Tab (conflicted with toggle_run,
                 which fires on bare Shift key-down) were both ruled out.
  Ctrl+Escape  → clear_target() — nulls current_target, clears the target
                 frame, turns off autoattack. Added 2026-08-23 so a misclick
                 can be undone without waiting out a Tab-cycle. The hardcoded
                 KEY_ESCAPE check in _unhandled_input (opens pause menu) is
                 guarded with `and not event.ctrl_pressed` so the two don't
                 both fire on Ctrl+Escape.
  Left-click   → PhysicsRayQueryParameters3D ray (150m) from camera through click
                 position. Only fires in MOUSE_MODE_VISIBLE. Selects clicked monster
                 AND triggers melee attack if in range (click = target + swing).
  _announce_target(node) — shared helper for tab and click; updates target frame
                 and logs target info to General tab.

--- Combat ---
  ` (backtick/tilde, attack_target action) → toggles autoattack; auto-attacks
                 current target each cooldown. (game_flow previously said "T" —
                 corrected 2026-08-23 to match the actual InputMap binding.)
  Spells       → Keys 1–9, 0, -, = fire action_bar_slots entries
  melee_attack input action exists in code but has no key bound (known gap).
  Attack sequence: calls CombatNode.resolve_attack() → full EQ-style roll chain
  All combat results routed through CombatLogFormatter for colored BBCode messages.

--- Spell Casting (cast_spell) ---
  Checks cooldown (_spell_cooldowns Dict), mana, target validity.
  Deducts mana, starts cooldown.
  Physical school (e.g. power_strike): base_damage + STR/2, mitigated by target AC,
    applied as physical (triggers monster resistances).
  Magical schools (arcane, fire, cold, etc.): CombatNode.calculate_spell_damage()
    adds INT-based arcane_power.
  Logs result via CombatLogFormatter.spell_damage() → GameLog.log_combat().
  spell_casting skill ticks on every successful cast.

--- Buff/Debuff Engine (CombatNode, added 2026-08-25) ---
  active_effects Dict on CombatNode: name -> {remaining, modifiers, tick_dmg,
    tick_interval, tick_accum}. apply_effect()/remove_effect()/has_effect()/

--- Aggro / Threat System (monster3d.gd, added 2026-08-25, chase-on-attack fixed 2026-09-13) ---
  Monster.aggro_table: Dictionary (attacker Node -> accumulated threat
  float). add_threat(attacker, amount) accumulates; get_current_target()
  returns whoever has the highest threat, falling back to `player` if the
  table is empty. state_chase()/state_attack()/perform_attack() all target
  get_current_target() instead of the hardcoded `player`.
  Initial engagement, FIXED 2026-09-13: add_threat() now itself calls
  change_state(State.CHASE) whenever amount > 0 and the monster is currently
  IDLE or PATROL — being attacked always starts a fight now. Previously
  add_threat() only recorded threat and never changed state; the ONLY thing
  that ever moved a monster into CHASE was can_see_player(), a pure
  proximity check (capped at MAX_AGGRO_DISTANCE=5m, as tight as ~1.67m for
  behavior_type=="passive" — smaller than the default 2m attack_range), so
  a monster could be hit repeatedly and never notice/retaliate/move if that
  much narrower sight check didn't also happen to pass. can_see_player() is
  UNCHANGED and still runs in state_idle()/state_patrol() too — it's just no
  longer the only path into combat. Threat-triggered engagement requires
  amount > 0 (add_threat's existing early-return), so a pure miss (0
  threat) still won't wake a monster on its own.
  Threat is generated at every player/pet damage/heal call site:
  player3d.attack_current_target(), player3d.cast_spell()'s enemy branch
  (life_siphon's self-heal also adds threat via generate_threat(0, healed) —
  this is what makes Necrotic Bastion's "+25% Life Drain healing... maintains
  threat generation through healing" actually keep aggro on the Voidknight),
  and pet_minion._perform_attack(). Each calls attacker.combat_node
  .generate_threat(damage[, healing]) then target.add_threat(attacker, that
  value) — generate_threat() already applies the attacker's own
  combat_node.get_modifier("threat_mult"), so a Shadow Ascendant Voidknight
  generates 35% less threat per hit, and if a pet is also fighting the same
  monster, the pet (no stance, full threat) will out-aggro the player and
  draw the attack instead.
  Guards are deliberately never part of this — monster3d.gd still has no way
  to target a guard at all (see Guard NPC below), so add_threat() is never
  called for guard attacks and guards never appear in any aggro_table.
  perform_attack() picks between the existing CombatLogFormatter
  .monster_attack() "hits you" messages (only when the resolved target is
  actually the player) and a new third-person _log_attack_on_other() for
  anything else (e.g. "Skeleton hits Skeleton Warrior for 12 damage!").
  change_state() logs "A Hooded Bandit attacks you!" (etc., via
  monster_description) the instant a monster enters CHASE with the PLAYER
  specifically as get_current_target() — added 2026-09-14, fires once per
  engagement (the existing same-state early-return prevents re-firing).
  NO LEASH, removed 2026-09-14 at the user's explicit request (EQ-style —
  "chases until it or you die," so a leash radius can't be used to shake a
  trained mob). state_chase() no longer has any distance-based give-up at
  all; aggro_table is no longer ever auto-cleared for this reason (a
  MAX_CHASE_LEASH_DISTANCE const existed briefly mid-session, fixing the
  wrong-reference-point version of the leash bug below, before being
  removed outright once "no leash" was the actual requirement).
  CHASE_SPEED_MULTIPLIER = 2.0, added 2026-09-14: handle_movement() doubles
  speed_3d only in State.CHASE (not PATROL, which stays at the mob's normal
  ambient pace) — most base speeds (2.5-3.5 m/s) trailed the player's 5 m/s
  walk, so an aggroed monster could be outrun at a stroll.

  THE REAL MOVEMENT BUG (found/fixed 2026-09-14, four layers deep): the
  above chase-on-attack fix (2026-09-13) was necessary but NOT sufficient —
  monsters still stood completely frozen under sustained attack. A
  single-frame snapshot test made the fix look confirmed; an 8-second real-
  physics trace exposed that it wasn't. In order, each found by continuing
  to trace after "fixing" the previous one:
    1. lumora_outskirts3d.tscn's baked NavigationMesh had ZERO vertices —
       never actually baked, despite NavigationRegion3D being present and
       enabled. Every path query returned nothing, so handle_movement()
       (used for PATROL and CHASE alike) always saw "no path" and did
       nothing — no movement, not even gravity. Re-baking at the default
       cell_size=0.25 (sized for small indoor spaces) failed outright —
       "Baking interrupted... would likely crash the engine" — the voxel
       grid for this ~180x120 unit outdoor zone was too large. Fixed:
       geometry_parsed_geometry_type=STATIC_COLLIDERS (bakes from the
       zone's own collision shapes, not GPU mesh data — faster, and what
       the bake warning itself recommended) + cell_size/cell_height=0.5,
       producing a real 466-vertex/391-polygon mesh. Saved as
       Data/lumora_outskirts_navmesh.tres, wired in as an ExtResource
       (navigation_mesh = ExtResource(...)) replacing the broken empty
       embedded SubResource.
    2. mob_spawner3d.gd hardcodes a flat Y per spawn entry
       (lumora_outskirts_spawns.json) that rarely matches real terrain
       height at the randomized X/Z, leaving mobs floating. A floating
       mob's first path waypoint becomes a near-pure vertical correction
       (~zero horizontal delta), which handle_movement()'s "nothing to do"
       check treated as "arrived" — frozen one layer deeper than bug #1.
       Fixed: _spawn() now snaps onto the navmesh via
       NavigationServer3D.map_get_closest_point(get_world_3d()
       .navigation_map, target_pos) before the mob enters the tree.
    3. Gravity itself was gated behind that SAME "nothing to do" check
       (it ran after the flat_dir.length()<0.1 early-return, never
       reached if that check fired) — so a monster whose navmesh waypoint
       height differed from its true resting floor height (the baked
       surface can legitimately sit above the real collision floor by a
       bit — measured up to ~0.7m on this terrain) could never fall/settle
       to the height that same check needed to pass. A pure deadlock.
       Fixed: handle_movement() restructured so velocity.x/z are computed
       conditionally (zero if no real horizontal step needed) but gravity
       + move_and_slide() run UNCONDITIONALLY every PATROL/CHASE tick.
    4. Even with 1-3 fixed, a monster hit from ~12m away took one step then
       froze again: NavigationAgent3D.get_next_path_position() doesn't
       advance past the CURRENT waypoint until the agent is within
       path_desired_distance (was 0.5) of it, using full 3D (Y included)
       distance — and the navmesh-vs-floor height gap from bug #3 alone
       already exceeded 0.5, so the agent could wait forever to close a
       vertical gap gravity was never going to let it close (it had already
       settled to the real floor). Fixed: path_desired_distance/
       target_desired_distance bumped from 0.5 to 1.5 in _ready().
  Verified end-to-end (not per-bug in isolation) with a real spawned bandit,
  hit from 6m away, tracked for 8 full seconds of actual physics: closes
  distance, switches to melee ATTACK on arrival, holds position there.

--- Patrol (added 2026-09-14, Session 38; movement rewritten Session 39;
    local obstacle steering + faster aggro scan added Session 41) ---
  @export patrol_waypoints: Array[NodePath] = [] — empty (default) keeps a
  guard exactly as before, stationary. Set to a list of Node3D/Marker3D
  paths and a guard walks them in order, looping forever. _setup_patrol()
  (_ready()) resolves each NodePath to a world position once
  (_patrol_points) and, if non-empty, sets _default_state = PATROL so
  combat returns there instead of IDLE. _process_patrol() advances to the
  next waypoint once within WAYPOINT_ARRIVAL (1.5) of the current one, via
  _move_toward().
  Third guard "Guard Bryn" in lumora_outskirts3d.tscn, patrol_waypoints
  pointing at six user-placed Marker3D nodes under a "Markers" node: Town
  Gate → Dock → South Zone → Traveling Merchant → Signpost → Archery
  Targets → (loops back to Town Gate) — a genuinely long, cross-map route
  (~4000+ units total), the first thing in this project to exercise
  NavigationAgent3D over serious distance rather than a short chase/local
  wander.
  _move_toward() manages its OWN corner list (_current_path:
  Array[Vector3]) via direct NavigationServer3D.query_path() calls, NOT
  NavigationAgent3D.target_position/get_next_path_position() — reworked
  2026-09-14 (Session 39) after three failed attempts (see change_log.txt
  for the full story) established that the agent's own cached path can go
  stale relative to the guard's actual position over a long route, in a way
  simply loosening its arrival tolerance or externally nudging position
  couldn't reliably fix — a query_path() called fresh from the guard's
  exact current position was consistently correct where the agent's own
  get_next_path_position() sometimes wasn't. _recompute_path() re-queries
  whenever _current_path is empty, the target moved > 0.5m, or the
  stuck-detector below requests one; CORNER_ARRIVAL (0.75) governs
  advancing through the cached corners. _current_path is explicitly cleared
  whenever combat ends and a patrolling guard returns to PATROL (fighting
  can move it well off whatever was cached pre-fight) and whenever
  _move_toward()'s own stop_distance is reached.
  _tick_stuck_detector() (STUCK_THRESHOLD=2.0s, STUCK_MOVE_EPSILON=0.1):
  if position hasn't moved more than a few cm in 2 seconds, sets
  _stuck_repath_requested so the next _move_toward() call forces a fresh
  query_path() — covers both a genuine navmesh/true-floor height mismatch
  (confirmed elsewhere in this project, up to ~0.7m) and any physical
  corner-wedge move_and_slide() might deflect a guard into, without needing
  to know or care which one actually happened.
  NavigationAgent3D's own path_desired_distance/target_desired_distance
  (0.75, up from the original 0.5) are still configured in _setup_combat()
  but no longer drive path-following — kept as-is since nothing currently
  reads them, low-risk to leave.
  _steer_around_obstacles(direction) (added Session 41, called from
  _move_toward() right before committing to a movement direction): a real-
  time local sidestep layered on top of the query_path()-based global
  routing above. Casts a short forward ray (OBSTACLE_CHECK_DISTANCE, 1.5m)
  along the intended heading; if clear, returns it unchanged; if blocked,
  tries alternate headings in order (OBSTACLE_AVOID_ANGLES_DEG: ±30°, ±60°,
  ±90°) and returns the first one that's actually clear, falling back to
  the original heading if none are (the stuck-detector recovers from that
  case instead). Added after a second stuck report at unrelated geometry
  (the wagon crash site, nothing to do with the gate Session 39 fixed) — the
  navmesh not cleanly routing around every piece of debris/prop collision
  on a ~4000-unit route turned out to be a general problem, not one bad
  spot, so this handles "something's in the way right now" independent of
  whether that specific geometry happens to be accounted for in the bake.

--- Spell Classification: skill_category vs. spell_school (finalized 2026-09-19,
    NOT YET IMPLEMENTED past skill_category — see status note at the end) ---
  Two fields on every player_spells.json entry that look redundant but answer
  different questions, per direct discussion this session:

  skill_category — WHICH SKILL levels up when this spell is cast (see Skill
    System above; _tick_skill(skill_category) is called on every cast,
    player3d.gd ~line 2859). Values are drawn from player_skills.json's real
    skill list: the 9 magic schools (abjuration, alteration, conjuration,
    divination, enchantment, evocation, illusion, necromancy, wild_magic),
    the 4 general magic meta-skills (spell_casting, concentration,
    channeling, meditation — always ticked alongside via the unconditional
    spell_casting tick), or a physical/martial skill (hand_to_hand, archery,
    parry, taunt, block, stealth, mantis_fist, etc.) for non-magic abilities.
    Source of truth: Data/Player Spells Classifications.xlsx (user-maintained
    spreadsheet, ~560 of 561 spells covered — gaps are content added after
    the spreadsheet snapshot, mainly Chaosborn's full kit and Voidknight's
    levels 4-8). Synced 2026-09-19: 41 mismatches found and fixed (mostly
    Troubadour's placeholder "musicianship" value replaced with real schools,
    plus a few trap/defense mismatches). One unresolved case:
    improved_pickpocket is shared by 3 classes (Shadowblade/Troubadour/
    Woodstalker) with conflicting spreadsheet categories (legerdermain vs.
    stealth) — needs a tiebreaker before it can be synced.

  spell_school — WHAT DAMAGE TYPE the spell's effect actually deals, for
    resistance purposes. Independent of skill_category: a spell can be
    trained via one skill but deal a differently-flavored effect (example
    discussed: Aetherfist's fire_strike trains "evocation" (skill_category)
    via a physical strike, but deals fire damage that mobs resist as magic,
    not via armor class — skill_category and spell_school genuinely diverge
    here). Finalized 10-value vocabulary (expanded from a D&D 3.5/5e-inspired
    list, refined in discussion — Psychic and Spirit deliberately kept
    separate despite similar surface flavor, since they protect two
    different class identities: Runecaster's mind-affecting kit (charm,
    mesmerize, dominate_mind) is genuinely mental/Psychic, while Gravecaller/
    Voidknight's kit (life_siphon, soul_harvest, wraith_call) is life-force/
    death drain/Spirit — merging them would make a mindless-undead-style
    "immune to mind effects" monster incorrectly also resist necrotic drain):
      physical  — melee/martial delivery, STR-scaled + AC-mitigated (existing
                  behavior, unchanged)
      fire, cold, acid, lightning — classic elemental damage types
      poison    — venom/toxin damage (distinct from disease)
      disease   — plague/infection/biological corruption (distinct from poison)
      magic     — generic/untyped magical force; the catch-all for spells
                  that aren't specifically elemental, mental, or death-flavored
      divine    — holy/radiant/sacred power (Lightsworn, Lightmender)
      psychic   — mind-affecting: charm, fear, domination, mental attacks
                  (Runecaster's core kit; Enchantment/Illusion schools)
      spirit    — soul/life-force/necrotic/undead/death magic (Gravecaller,
                  Voidknight; Necromancy school)
    Rough school→spell_school starting point (Evocation/Necromancy/Alteration
    need PER-SPELL judgment since they span multiple damage types depending
    on the specific spell's description, not a fixed 1:1 mapping):
      Abjuration   → magic (barriers/wards; divine if explicitly holy)
      Alteration   → magic (shape/form change; per-spell if it deals damage)
      Conjuration  → physical or magic (mostly about the summon, not a damage
                     type of its own — see summon_* spells)
      Divination   → n/a (utility, rarely deals damage; psychic if offensive)
      Enchantment  → psychic
      Evocation    → fire/cold/acid/lightning/magic/divine — PER-SPELL, this
                     is the school that spans every element; read each
                     spell's own description for its actual damage type
      Illusion     → psychic
      Necromancy   → spirit (primary), poison/disease (per-spell, e.g. plague
                     spells), magic (generic drain effects)
      Wild Magic   → magic + random elemental (Chaosborn; intentionally
                     chaotic, no fixed mapping)

  IMPLEMENTED 2026-09-19 — skill_category fix applied and verified (see
  above). spell_school fully reclassified: 457 of 561 spells' spell_school
  updated via a script matching keyword-detected damage type in the
  description FIRST (so a physically-delivered attack with an elemental/
  status effect — Aetherfist's fire_strike, Shadowblade's venom_strike —

--- Spell Icons & Tooltips (added 2026-09-19, Session 49) ---
  Every spell in player_spells.json may carry an "icon" field (res:// path into
  Assets/icons/spells/, same format as items.json). Spells with no matching
  icon file simply have no field and fall back to their text label. The 49
  icon files are named <prefix><kind>.png:
    prefix  self   = cast on yourself
            target = single target (an enemy, or one ally)
            group  = player group when beneficial, all enemies around the
                     cast target when detrimental (user's design, 2026-09-19)
            aoe    = pbaoe/cone/line — radiates from the CASTER
    kind    heal, hot, buff, ward, dispel, stun, root, fear, blind, silence,
            plus damage types: fire, ice(cold), lightning, poison(+disease),
            divine, arcane(magic+psychic), necromancy(spirit)
    misc    petsummon, totemsummon, resurrect, teleport, (tracking: unused)
  Assignment is done by tools/assign_spell_icons.py (dry run by default,
  --write to rewrite the field; idempotent — re-run after adding icon files
  or changing a spell's target/effect_type). Rules, in order: teleport /
  resurrection / totem / summon special cases → beneficial-vs-hostile (from
  effect_type, spell_type, and description wording, since ~64 spells are
  tagged target "enemy" but are really self buffs/forms/shields — those get
  self* icons) → kind → prefix from the `target` field. Exceptions: a
  beneficial "group" spell whose description names only a single ally gets
  target* (that is how player3d.gd actually casts those today); improved_/
  enhanced_/greater_/master_ upgrades share their base spell's icon. No
  physical-damage icons exist yet, so 40 physical attacks have no icon.
  Non-obvious fallbacks: snare→root, mesmerize/confuse→stun, charm→arcane,
  pbaoe crowd-control→group CC icons (no aoe CC art exists).
  Shared helper: Scripts/spell_info.gd (class_name SpellInfo) —
  icon_texture(info) (cached load), wrap_text() (Godot tooltips never wrap;
  NOT named wrap — that collides with GDScript's global wrap()), and
  tooltip(spell_name, info) = name + description + "N mp · Ns recast".
  Used by three UIs, all showing the same tooltip source (the file's own
  description):
    action_bar.gd    — slot icon_rect under the key/badge labels; name label
                       hidden when an icon shows; tooltip on the slot Panel.
                       Skills ("K" slots) and icon-less spells keep text.
    abilities_book.gd — 40px icon left of each Class Skills row; row tooltip;
                       drag preview is the icon.
    buff_bar.gd      — icon inside the existing 28px box (box is
                       MOUSE_FILTER_IGNORE so hover reaches the row's
                       tooltip); stances/environmental effects stay blank.
  Known quirk: buff_bar's red debuff highlight keys off target == "enemy", so
  the ~64 mis-tagged self buffs (e.g. lights_bastion) render red if applied.

================================================================================
COMBAT NODE (combatnode.gd)
================================================================================

Class: CombatNode extends Node
Added as child to both Player3D and Monster.

--- 7 Base Stats ---
  strength, constitution, dexterity, intelligence, wisdom, charisma, luck

--- Derived Stats (recalculate_derived_stats, cached until _stats_dirty) ---
  max_hp     = 50 + con*10 + class_hp_bonus + gear_hp
  max_mana   = 30 + (int+wis)*5 + class_mana_bonus + gear_mana
  armor_class = 10 + gear_ac + dex/2 + class_ac_bonus + shield_bonus
  attack_rating = weapon_skill*2 + str + dex/2 + gear_atk
  crit_chance = 5 + (dex+luck)/2 + class_crit_bonus + gear_crit  (cap 60%)
  dodge = class_dodge_base + dex*0.5  (cap 50%)
  parry = class_parry_base + dex*0.3 + weapon_skill*0.1  (cap 50%)
  riposte = class_riposte_base + dex*0.2 + weapon_skill*0.1  (cap 100%)
  arcane_power = int*2 + gear_spell_power
  hp_regen = 2 + int(con/3)  (per 6s tick; ×3 while sitting)
  mana_regen = 1 + wis/5  (per 6s tick)
  carry_weight = 100 + str*2

--- resolve_attack(target: CombatNode) → Dictionary ---
  Full attack resolution in order:
  1. Miss check (roll vs hit_chance)
  2. Riposte check (target parries + ripostes → attacker takes damage)
  3. Parry check (target parries)
  4. Block check (target blocks, requires shield)
  5. Dodge check (target dodges)
  6. Hit → calculate_melee_damage() → apply_ac_mitigation() → target.current_hp -= dmg
  Returns: {result, damage, is_crit, message}

  IMPORTANT: step 6 already applies the damage directly to
  target.current_hp — resolve_attack() is a complete, self-contained damage
  application, not just a calculator. A caller must NOT also call
  target.take_damage()/apply_damage() for the same hit, or it double-applies.
  Bug fixed 2026-09-14 (Session 33): monster3d.gd's perform_attack() did
  exactly that for monster-vs-player hits (resolve_attack() applied the hit,
  then also called player.take_damage(result["damage"], ...) for the same
  hit) — monsters were dealing EXACTLY DOUBLE damage to the player, verified
  with a headless test (18/47 raw damage from resolve_attack() landing as
  36/94 through the full call). Player-vs-monster (player3d.gd),
  guard-vs-monster (guard_npc.gd), and pet-vs-monster (pet_minion.gd) were
  all already correct — only the monster-vs-player direction had the
  redundant second call. Fixed by removing it; monster3d.gd now calls
  player3d.gd's on_combat_node_hit(attacker) instead, which handles ONLY the
  side effects resolve_attack() doesn't already cover (auto-target-switch,
  the incapacitation check — see player3d.gd's death system below) without
  touching HP again.

--- Other attack modes ---
  resolve_dual_wield_attack() — main + offhand (-10% hit)
  resolve_aetherfist_attack() — flurry: main + optional double (lv10+) + triple (lv15+)

--- get_resistance(resist_type) / calculate_spell_damage() ---
  get_resistance(resist_type) appends "_resist" to its argument itself and
  looks up the derived stat. Bug fixed 2026-09-14 (Session 28): both
  calculate_spell_damage() and the dead/unused calculate_resist_chance() were
  calling it with an ALREADY-suffixed key ("arcane_resist"/"divine_resist"),
  producing a lookup for the nonexistent "arcane_resist_resist"/
  "divine_resist_resist" — always 0. Spell damage had never actually been
  resisted by any target, player or monster, until this fix. Call sites now
  pass the unsuffixed "arcane"/"divine".

--- Spell interrupt (interrupt_spell) ---
  Checks concentration roll against cast progress.
  On failure: deducts mana scaled to how far cast had progressed.

--- Class bonuses ---
  set_class(new_class) applies class-specific hp_bonus, ac_bonus, dodge_base,
  parry_base, riposte_base, concentration_base.
  Classes: Blademaster, Aetherfist, Shadowblade, Voidknight, Lightsworn,
           Woodstalker, Troubadour, Spiritweaver, Gravecaller, Runecaster,
           Arcanist, Chaosborn


================================================================================
MONSTER SYSTEM (monster3d.gd)
================================================================================

Class: Monster extends CharacterBody3D
Group: "monsters"
Scene: Scenes/monster_template.tscn (base) + individual [name].tscn

--- Loading ---
  _ready(): reads monster_name (from @export or get_monster_name() override)
  → load_monster_stats() reads Data/monsters.json
  → configures CombatNode via _configure_combat_node()
  Balance pass, 2026-09-14 (Session 28): base stats are NO LONGER flatly zero —
  they used to be, which silently collapsed monster accuracy AND zeroed all
  magic resistance (get_resistance() always returned 0% for every combatant,
  see the combatnode.gd note below). STR/CON/DEX = 8 + level*3, INT/WIS/CHA/LUCK
  = 5 flat. gear_hp/gear_ac still back-calculate so the JSON's hand-tuned
  max_health/armor_class stay authoritative on top of the new base stats.
  gear_atk = 15 + level*5 (unchanged) for hit rates of ~55-60% vs typical player AC.

--- State Machine ---
  IDLE    → patrols after a randomized wait; aggro if player in aggro_range (≤5m)
  PATROL  → moves to random patrol points; aggro if player spotted
  CHASE   → uses NavigationAgent3D to path to player; attack when in range
  ATTACK  → looks at player, calls perform_attack() on cooldown
  DEAD    → no further processing; triggers loot roll and despawn timer

  IDLE→PATROL timing (reworked 2026-09-14, Session 34): a deterministic
  timer, not the old 1%-per-frame RNG roll. Non-passive behavior_types wait
  _idle_duration seconds (randf_range(IDLE_MIN_DURATION, IDLE_MAX_DURATION)
  = 2–5s, rolled on entering State.IDLE via change_state()'s IDLE case) then
  switch to PATROL; passive types never do (stay put until aggroed, same as
  before). pick_new_patrol_point() rolls a distance between
  PATROL_MIN_DISTANCE (5) and PATROL_MAX_DISTANCE (18) from spawn_position —
  was a flat 0–10 with no minimum, which combined with the old slow RNG
  trigger made monsters read as essentially static (confirmed headlessly:
  ~3 units of net movement over 12s before this pass, ~14 units of total
  path covered over 10s after).

  Aggro range: JSON values scaled by AGGRO_RANGE_SCALE=10.0, hard capped at
  MAX_AGGRO_DISTANCE=5.0m. Passive (÷3) and neutral (÷2) behavior type
  modifiers applied before the cap. Leash check uses same effective range.
  can_see_player() also returns false outright whenever player.dying is true
  (added 2026-09-14, Session 33) — a monster in IDLE/PATROL won't re-aggro a
  downed/dead-pending-respawn player no matter how close it is; see the
  disengage-on-death behavior below.

  Gravity always applied for all states (IDLE/ATTACK also call move_and_slide
  with gravity) so monsters never float.

--- perform_attack() ---
  Calls CombatNode.resolve_attack(player.combat_node) — this call ALONE
  applies the hit's damage (see the resolve_attack() note above). Routes
  result through CombatLogFormatter.monster_attack() → GameLog.log_combat(),
  then calls player.on_combat_node_hit(self) for the non-HP side effects
  (auto-target-switch, incapacitation check) — NOT player.take_damage(),
  which would double-apply the hit (this was a real, serious bug until
  Session 33 — see the resolve_attack() note above).
  Social monsters (is_social=true) call call_nearby_allies() — same faction
  monsters within ASSIST_RANGE (5.0m, a real meter distance) switch to
  CHASE. Bug fixed 2026-09-14 (Session 34): this used to compare a real
  meter distance against aggro_range, which is documented above as the RAW
  unscaled JSON value, not meters — a bandit's aggro_range is 200.0, so
  allies anywhere in roughly a 200m radius would come assist. Now a
  dedicated ASSIST_RANGE constant, decoupled from aggro_range entirely.

--- Disengage on player death (force_disengage(), added 2026-09-14, Session 33) ---
  Called on every monster in group "monsters" the instant the player becomes
  incapacitated (player3d.gd's die()). Clears aggro_table and, if currently
  CHASE/ATTACK, switches to PATROL with patrol_target forced to
  spawn_position (overriding change_state()'s own random nearby point) —
  walks straight back to its spawn area instead of wandering off randomly.
  Combined with can_see_player()'s player.dying check above, a monster won't
  pick the fight back up even if the still-incapacitated player is standing
  right next to it during the ~20s bleed-out window (see player3d.gd's death
  system below) — the encounter is simply over from the monster's side.

--- Monster death lines (Data/humanoid_death_lines.json, added 2026-09-14, Session 33) ---
  die() logs a random line from this file (NPCFlavorText, same loader
  guard_flavor_text.json uses — {"death": [...]}, one category, user-editable)
  for any monster whose category is "humanoid" (bandits, goblins, dustwalker
  variants, etc.) — NOT "undead" (skeletons, mummy, mirage_phantom), which
  wouldn't make sense saying last words. Logged via GameLog.log_general(),
  attributed to the monster by monster_description/name, same
  "$Name says, ..." convention guard_npc.gd uses.

--- XP Award on die() ---
  Finds player via group, adds xp_gain to Global.player_data["xp"].
  Logs "You gain X experience points. (current/next)".
  Level-up loop handles multiple levels in one kill: increments player_level,
  looks up next threshold from Global.xp_table, logs gold level-up message,
  calls player.on_level_up() to sync CombatNode and restore HP/Mana to full.

--- Loot on die() ---
  Rolls _load_loot_data() from Data/solgrave_expanse_loot.json.
  Rolls category_loot_tables[category] (e.g. "undead", "animal") — this is a
  universal per-category floor (populated 2026-09-14, Session 28; was empty
  before, a big part of why loot felt sparse regardless of species) that fires
  in ADDITION to the mob's own species table below, not instead of it.
  Rolls zone_loot_tables for monster-specific drops by name (searches every
  zone sub-table in the file regardless of the mob's own `zone` field — see
  _find_mob_loot()).
  Results combined into pending_loot; is_lootable = true if non-empty.
  60s auto-despawn via await (guarded with is_inside_tree() check).
  Every item referenced by a lumora_outskirts-reachable loot table now has a
  real entry in Data/items.json (Session 28 added 10 that were missing —
  scarab_eye/scarab_shell/beetle_wing/sand_shimmer/shiny_pebble/venom_sac/
  spider_fang/embalming_salve/canopic_jar_fragment/rotten_linen — item IDs the
  loot tables already referenced but that had no definition, so
  Inventory.get_item_definition() returned empty and the drop silently
  couldn't be looted/displayed properly).

--- open_loot_window() ---
  Instantiates corpse_loot_window.tscn, calls setup(name, pending_loot).
  pending_loot is passed by reference — taking items depletes the array.
  Connects all_looted → _on_fully_looted() → 5s despawn.

--- Child Monster Classes ---
  Each extends Monster, overrides get_monster_name() to return the key used
  in monsters.json. Optionally overrides modify_damage() for type resistances.
  Example — skeleton3d.gd:
    piercing → 70% (resistant)
    blunt    → 130% (weak)
    fire     → 110% (weak)
  Pattern applies to all mobs in Scripts/: bat, rat, slime, snake, spider,
  goblin, ghost, bandit, bonegnawer, dune_scarab, dustwalker variants,
  khepri_beetle, lumora_outrider, mirage_phantom, mummy, sand_stinger,
  sandshifter, sunmaddened_wanderer, thornback_lizard, wild_dog.

================================================================================
PLAYER DEATH / INCAPACITATION / RESPAWN (player3d.gd, added 2026-09-14, Session 33)
================================================================================

EQ-style: 0 HP doesn't kill outright, it incapacitates. dying: bool (already
existed, froze movement via _physics_process()'s "if dying: return" and
regen/vitals via _process()'s — previously nothing ever cleared it back to
false, so hitting 0 HP was a permanent, unrecoverable freeze) is now the
"can't act" gate for BOTH sub-states below, cleared again on respawn.

--- Sequence ---
  1. combat_node.is_alive() goes false (from on_combat_node_hit() — a
     monster hit — or a riposte while the player is attacking) → die(attacker).
  2. die(attacker): dying=true, is_incapacitated=true, clamps
     combat_node.current_hp to exactly 0 (resolve_attack() doesn't clamp —
     a big single hit can overshoot well below 0), captures attacker's
     description as _last_attacker_desc, logs "You collapse, bleeding
     out...", turns off autoattack, and calls force_disengage() on every
     monster in group "monsters" (see monster3d.gd above) — the fight is
     over immediately, nothing can interrupt the bleed-out that follows.
  3. _tick_bleedout(delta), driven from _process() (runs even though dying
     is true — checked BEFORE the early-return): counts up to
     BLEED_OUT_DURATION (20s), logging "You are bleeding out..." every
     BLEED_OUT_WARN_INTERVAL (5s). Purely passive/deterministic — no more
     combat damage can land (monsters disengaged), and regen is frozen too
     (existing dying gate), so there's no self-stabilizing mid-bleed-out.
  4. At BLEED_OUT_DURATION, _die_for_real(): is_incapacitated=false, logs
     "You have been defeated by <_last_attacker_desc>!" (red), then a random
     line from Data/player_death_flavor.json (NPCFlavorText, own wording —
     NOT copied from any specific reference), then _show_death_screen() — a
     full-screen black CanvasLayer (layer 100) reading "RETURNING TO YOUR
     BIND POINT..." — held for RESPAWN_DELAY (3s) via
     `await get_tree().create_timer(...)`.
  5. _respawn(): frees the death screen, teleports global_position to
     get_bind_point(), restores HP/mana/stamina to full, clears
     current_target/target_frame, dying=false. Logs "You awaken at your
     bind point."

--- Bind point ---
  No bind spell/NPC exists yet. _ensure_bind_point() (called once from
  _ready(), after load_player_data_from_global()) defaults it to wherever
  the character first spawns into the world if Global.player_data has no
  "bind_point" key yet. Stored as a plain [x,y,z] Array (Vector3 isn't
  JSON-serializable) — get_bind_point() reads it back, falling back to the
  player's current position if somehow unset. A future bind spell/NPC only
  needs to overwrite Global.player_data["bind_point"] — nothing else
  changes.


================================================================================
VITALS: SATIETY / THIRST (player3d.gd, made functional Session 29 — 2026-09-14)
================================================================================

satiety/thirst: int 0-100, decay over real time via update_vitals_decay()
(called every _process() frame; the decay itself only ticks every
DECAY_INTERVAL=60s). satiety -1/tick (~100 real min to fully drain from 100),
thirst -2/tick (~50 min — twice as fast, deliberately, so water needs more
frequent attention than food).

--- Regen gating (the actual point of the system) ---
  satiety <= 0: HP regen (in _process()'s REGEN_INTERVAL block) AND movement
    stamina regen (update_stamina()) both skip entirely — not a percentage
    reduction, a hard stop.
  thirst <= 0: mana regen skips entirely, same hard stop.
  Below 25 (but still >0): soft warning-zone penalty only — 0.8x regen
    (get_stat_penalty() also applies a small 5%/10% melee damage penalty,
    unrelated function, unchanged by this pass).
  Edge-triggered GameLog warnings (not spammed every tick) at the <25 and
  <=0 thresholds for both — see _hunger_warn_stage/_thirst_warn_stage.

--- Consuming food/drink ---
  consume_food_or_drink(item: Dictionary) — reads item["restores"]
  ("satiety" or "thirst") and item["restore_amount"], adds to the matching
  vital (capped at 100), logs a random flavor line from
  Data/food_drink_flavor.json (via NPCFlavorText — "You consume X. Yumm!
  That was tasty!" / "You quench your thirst with X. Ahhh! That hit the
  spot.", changed 2026-09-14 Session 42, replaces the old plain "You eat X.
  (Hunger: N/100)" message), then calls _update_well_fed_buff(). Triggered
  two ways:
    - Manual: slot_button.gd's right-click inspect popup — an "Eat"/"Drink"
      button appears for any item whose items.json "type" is "food"/"drink".
    - Automatic (added 2026-09-14, Session 42): update_vitals_decay() calls
      _try_auto_consume("satiety"/"thirst") the moment either vital ticks
      below 25 (the existing "low" warning threshold) — finds the first
      matching item via Inventory.find_first_by_restores() (basic slots,
      then bags) and eats/drinks it automatically, no player action needed.
      Falls through to the normal low/empty GameLog warnings unchanged if
      nothing suitable is carried.
  Both paths consume exactly one unit via
  Inventory.consume_one(slot_type, slot_index, bag_slot, item_index) —
  decrements a stack's quantity, or removes the slot/bag entry entirely at
  quantity 1.
  Food/drink items in Data/items.json: trail_rations (+8 satiety, 2cp),
  iron_rations (+15 satiety, 4cp), spring_water (+8 thirst, 1cp),
  water_flask (+15 thirst, 2cp). Real characters start with 20 of each
  ration/flask (character_creation.gd's build_starting_inventory()).

--- Well Fed buff ---
  Re-evaluated every vitals tick (not a fixed-duration timer): while both
  satiety AND thirst are >= WELL_FED_THRESHOLD (75), combat_node has the
  "well_fed" effect applied (+2 hp_regen/mana_regen/stamina_regen_bonus,
  same generic apply_effect() system campfire.gd/stance_bar.gd use — shows
  up on the buff bar automatically, see buff_bar.gd's
  ENVIRONMENTAL_EFFECT_DESCRIPTIONS). Removed the moment either drops below
  75 — no separate expiry timer needed since it's just re-checked each tick.

--- HUD ---
  player_frame.tscn/.gd: Food/Water progress bars (orange/teal) below the
  existing HP/MP/STA rows — the first player-visible readout of these vitals
  at all; before this pass they decayed silently.

  position (same project_ray_origin()/project_ray_normal() pattern
  _try_click_target() already uses for left-click monster/guard targeting)
  and only returns a hit if it's precisely on that VendorNPC's own collision

  Gated on `not Global.mouselook_enabled`, NOT `Input.mouse_mode ==
  MOUSE_MODE_VISIBLE` — bug fixed 2026-09-14 (Session 37): the initial

================================================================================

  1. Reads Global.character_options (loaded by Global._ready from
     Data/character_options.json) for race and class lists.

  6. On Begin: Global.load_player_data_from_file() → scene change to
     lumora_outskirts3d.tscn.

SAVE / LOAD SYSTEM
================================================================================

Save file: user://saves/{character_name}_character_stats.json

Contents:
  player_name, player_class, player_race, player_level
  stats: {strength, constitution, dexterity, intelligence, wisdom, charisma, luck}
  current_hp, current_mana
  xp, xp_next_level
  copper, silver, gold, platinum
  satiety, thirst, current_stamina, max_stamina
  known_spells[], known_skills[], action_bar_slots[]
  skill_levels: {skill_name → level}
  equipment: {slot → item_id}      ← legacy, used for first-load compat only
  inventory_data: {basic_inventory, bag_contents, bank_storage, equipped}
  ui_positions: {chat: [...], action_bar: [...], chat_font_size: int}
  resistances: {acid, cold, fire, magic, psychic}
  character_creation: {real_time, game_time}
  playtime_seconds
  bind_point: [x, y, z]   ← death-respawn location, set once on first spawn
  last_position: [x, y, z] ← added 2026-09-14 Session 42, see below

Auto-saved when:
  - Any equipment slot changes (Inventory.equipment_changed signal)
  - action_bar or chat window is dragged and released
  - A spell is learned from a scroll
  - Save Game is pressed in pause menu
  - Save & Exit is pressed in pause menu

Player position (added 2026-09-14, Session 42): Global.save_player_data_to_file()
  captures the live player's global_position into player_data["last_position"]
  itself, right before every write — centralized here rather than patched into
  each of the several call sites above, so a future new save call site can't
  forget it. player3d._restore_last_position() (runs in _ready(), after
  load_player_data_from_global(), before _ensure_bind_point()) applies it back
  on load; no-op for a brand new character, which just keeps the zone's default
  Player3D spawn transform. Distinct from bind_point (death respawn) — logging
  out and dying return you to different places, same as EQ.

Load path:
  main_menu → load_game → Global.set_player_data() → scene change
  → player3d.load_player_data_from_global()
  → load_character_data() sets CombatNode stats
  → Inventory.load_inventory_data() restores all bags/equipment
  → _apply_equipment_from_inventory() syncs CombatNode weapon_damage + gear_ac
  → skill_levels Dict loaded, _sync_weapon_skill() applied

KEY SIGNAL FLOWS
================================================================================

Equipping an item:
  Inventory.equip_item()
    → Inventory.equipment_changed emitted
    → player3d._on_equipment_changed()
    → _apply_equipment_from_inventory() → CombatNode updated
    → Global.save_player_data_to_file()

Logging a combat event:
  Any script calls GameLog.log_combat("text")
    → GameLog emits combat_message
    → game_log_window._on_combat() appends to Combat tab RichTextLabel

Toggling autoattack:
  player3d.handle_combat() detects "attack_target" input
    → GameLog.set_autoattack(bool)
    → game_log_window._on_autoattack_changed() shows/hides flashing dot

Monster dies and gets fully looted:
  corpse_loot_window emits all_looted
    → monster3d._on_fully_looted()
    → 5s await → loot_window.queue_free() + monster.queue_free()

Monster dies without looting (60s timeout):
  monster3d.die() → await 60s → if is_inside_tree(): queue_free()

Currency looted:
  corpse_loot_window._apply_drop()
    → Global.grant_currency(type, amount)
    → Global emits currency_changed  (no UI listener yet — future HUD work)

Monster kill → XP → level up:
  monster3d.die()
    → Global.player_data["xp"] += xp_gain
    → level-up loop checks xp_table thresholds
    → player.on_level_up() → CombatNode synced, HP/Mana restored to full

Spell learned from scroll:
  slot_button._learn_from_scroll()
    → player.known_spells.append(spell_name)
    → Inventory.remove_from_basic_inventory()/remove_from_bag() removes scroll
      (now also emits inventory_changed so backpack_ui repaints immediately —
      fixed 2026-08-25; previously the scroll stayed visually in the backpack
      until an unrelated inventory action forced a redraw)
    → Global.save_player_data_to_file()
    → abilities_book refreshed if open

Hailing a guard or vendor NPC (H key or "/hail", added 2026-08-25, extended
to vendors 2026-09-14 Session 36; vendor hail now opens the shop Session 42):
  player3d.try_hail_nearby_npc() finds nearest "npc_guard"/"npc_vendor"
  group member within 5m
    → if it's a VendorNPC: calls _open_shop(nearest) directly (opens the
      shop window AND greets, changed Session 42 — see VENDOR / SHOP's
      Greeting section)
    → otherwise dispatched via has_method("respond_to_hail") so the caller
      doesn't need to know the NPC's concrete type
        → guard_npc.respond_to_hail() → GameLog.log_general() with a
          random Data/guard_flavor_text.json line

Following an NPC or player, "/follow [name]" (added 2026-09-14, Session 42):
  game_log_window._handle_slash_command() → player3d.try_follow(query)
    → empty query: follows current_target (Tab/left-click); else searches
      groups "npc_guard"/"npc_vendor"/"monsters"/"player" by
      case-insensitive substring match on TargetFrame.display_name(),
      nearest wins
    → start_following(target) logs "You begin following X."; calling
      /follow again on the same target calls stop_following() instead
      (toggle off)
  Every physics frame thereafter, handle_movement() checks _follow_target
  first: any manual movement input (forward/back/strafe/turn/jump) calls
  stop_following() and falls through to normal player-controlled movement
  for that frame; otherwise _handle_follow_movement() steers toward the
  target using NavigationServer3D.query_path() directly — the same
  self-managed approach guard_npc.gd's patrol system uses (Session 39/41)
  instead of NavigationAgent3D, repathing every 0.75s
  (FOLLOW_REPATH_INTERVAL) and stopping 3m short (FOLLOW_STOP_DISTANCE).
  Also stops itself if the target goes invalid (is_instance_valid() check).

Summoning/commanding the spectral minion pet (added 2026-08-25):
  player3d.cast_spell("spectral_minion") → _summon_spectral_minion()
    → frees any existing active_pet/active_pet_frame, instances pet_minion.tscn
      + pet_frame.tscn, pet.setup(player)
  pet_frame.gd buttons → pet.cmd_attack()/cmd_stop()/cmd_back()/cmd_follow()/
    cmd_sit()/cmd_guard() → sets pet.command, drives pet_minion._physics_process()

Toggling a stance (added 2026-08-25):
  stance_bar.gd slot click → combat_node.apply_effect("stance_"+id, INF, modifiers)
    (or remove_effect() if toggling off / switching) → player3d.current_stance updated

================================================================================
SPELL CASTING — CAST TIME / INTERRUPT / CAST BAR (added 2026-09-17, Session 44)
================================================================================

- `combatnode.gd` had unused scaffolding for real cast times since well before
  this session (`is_casting`, `current_cast_time`, `total_cast_time`,
  `start_spell_cast()`, `interrupt_spell()`) and every spell in
  `player_spells.json` already carries a `casting_time` field — none of it was
  actually wired up. `cast_spell()` used to resolve every spell's effect
  instantly, with the "begin cast" log line as pure flavor text.
- Now real: `player3d.gd`'s `cast_spell()` validates the cast (target/mana/
  cooldown), commits mana+cooldown, then either resolves immediately
  (`casting_time <= 0`) or stores the pending spell/target and calls
  `combat_node.start_spell_cast(cast_time)`. `_tick_spell_cast()` (called every
  physics frame alongside `_tick_cooldowns()`) counts the cast down and calls
  `_resolve_spell_cast(spell_name, spell, target_node)` once it completes —
  the actual spell-effect logic (the old cast_spell() body) now lives in that
  function. Guards against the target having died/been freed mid-cast by
  checking `is_instance_valid()` before passing it in (a freed object in a
  typed Node parameter crashes outright otherwise — this was a real bug found
  via a pet dying mid-heal).
- Interrupt: taking damage while `is_casting` (player3d.gd's `take_damage()`/
  `on_combat_node_hit()`) calls `_check_spell_interrupt()`, which uses
  `combat_node.interrupt_spell()`'s concentration-roll (boosted by cast
  progress) to decide whether the cast survives. Fixed a real bug in
  `interrupt_spell()` while wiring it up: it used to set `is_casting = false`
  unconditionally before checking success/failure, so even a successful
  concentration check silently canceled the cast — success now just logs and
  lets the cast continue.
- UI: new `Scenes/cast_bar.tscn` / `Scripts/cast_bar.gd` — spell name, a
  filling ProgressBar (yellow), time remaining, only visible while
  `combat_node.is_casting`. Draggable, position-persisted via `WindowPosition`
  like every other HUD frame (only draggable while actually visible, i.e.
  mid-cast).
- Applies to every caster class uniformly — this isn't a per-class feature.

SESSION 50 UPDATE (2026-09-19) — how a multiplayer game is assembled now (supersedes the older

- JOIN ORDER: Net.begin_join(address) loads the zone FIRST; the zone root's multiplayer_player_spawner.gd
  connects from _ready (Net.complete_pending_join()). Godot drops any spawn whose spawner node doesn't
  exist yet and never resends it, and the host replicates the instant a peer connects — so connecting from
  the menu and loading the zone afterwards left joiners without their character/monsters/host name.
  A failed join or a lost server returns to the main menu with Net.last_failure_reason.
- EVERY PLAYER IS SPAWNED: in multiplayer the zone's pre-placed player3d is dropped
  (Net.omit_preplaced_player -> player3d.gd _enter_tree()); host and joiners alike come from PlayerSpawner at
  the spawner script's spawn_position. Net.is_dedicated_server = the host has no character (no spawn for peer 1).
  Single-player still uses the pre-placed node.
- AUTHORITY MAP: server owns monsters/spawn table/weather/world clock/guards+Oni; each player owns their own
  movement, HP/MP, inventory and save file (replicated outward); pets are owner-authoritative.
- MONSTER -> PLAYER HITS: the server does NOT resolve a swing on a remote player's stat-less puppet (HP replicates

  channel (dropdown + /say /party /zone /tell); plain text goes to it. Say is range-filtered on the SENDER (10 m, replicated positions)

  now relay too (`monster3d.gd`'s `cmd_*()` apply locally first for instant
  UI feedback in `pet_frame.gd` — `command`/`charm_attack_target` aren't
  replicated fields — then relay via the new `apply_networked_charm_command`
  RPC when the caster isn't the real authority). `cmd_attack`'s target
  crosses the wire as a `NodePath` string (a Node reference means nothing
  cross-machine, same rule as `apply_charm`'s owner param), resolved back to
  a real node via `get_node_or_null()` on the receiving end.
- Also found and fixed while closing out the above: a charmed monster's kill
  of another monster didn't pass `credited_peer_id`, so it would have
  wrongly credited the host instead of whoever actually cast the charm;
  DoT effect_type spells cast on a monster weren't routed through the relay
  helper at all (copy-paste miss, same fix as its siblings); and Shadow
  Aura's continuous per-tick nearby-enemy debuff (`_tick_active_spell_effects()`)
  had the same non-relayed mutation. Also fixed a related but distinct bug in
  `campfire.gd`: its warmth Area3D runs identically on every peer and
  detects ANY replicated body (including a remote player's puppet) entering
  it, so a non-owning peer could apply the warmth buff directly to someone
  else's combat_node and print the "you feel invigorated" message on the
  wrong screen — fixed with an `is_multiplayer_authority()` gate on the body
  itself (a player is always self-authoritative, so no RPC relay was needed
  here, just the right gate).

- Personal/instanced loot (Session 46, 2026-09-17): `monster3d.gd`'s
  `pending_loot`/`is_lootable` were non-replicated fields only ever set
  inside `die()`, which only ever runs on the authoritative/host machine —
  so a non-host player could not loot a corpse AT ALL, not just "the same
  drops as everyone else" as first reported. Fixed by rolling loot lazily,
  per-peer, the first time each peer opens the window (`_personal_loot:
  Dictionary` keyed by peer id, populated inside `open_loot_window()`
  instead of `die()`) — a script field not listed in a node's
  `SceneReplicationConfig` is already implicitly per-peer, so this one
  redesign fixes both "shared loot" and "non-host can't loot" at once. The
  corpse itself no longer frees on the first player's last item — it rides
  out its normal 60s despawn timer so every player gets a fair window; an
  empty personal loot window auto-closes 5s after the last item is taken.
- Combat log now crosses the network (Session 46, 2026-09-17): `GameLog`
  (`game_log.gd`) is a purely local signal bus with no networking of its
  own, so a second player never saw the first player's attacks/spells/buffs
  land, even standing right next to them. `net.gd` gained a combat-message
  relay (`broadcast_combat_message()` / `_rpc_receive_combat_message`,
  same shape as the existing `/tell`/`/party` RPCs) that every other
  connected peer feeds into their own `GameLog.log_combat()`, tagged with
  the acting player's position so the receiver's existing 10m
  `COMBAT_VISIBILITY_RANGE` filter (`game_log_window.gd`, already used to
  hide distant NPC fight noise) applies automatically — no separate
  proximity system needed. `player3d.gd`'s `_broadcast_combat()` helper
  fires this alongside every local melee/spell/buff/death message. Most of
  `_apply_generic_spell_effect()`'s messages ("Target is weakened.", etc.)
  were already caster-agnostic (never say "You") and broadcast verbatim,
  except when the target is the caster's own "yourself" placeholder, which
  swaps to the caster's real name (`bcast_desc`) so it doesn't read as
  nonsense on someone else's screen. `CombatLogFormatter` gained third-
  person variants (`player_attack_broadcast()`, `spell_cast()`) for the
  handful of messages that do hardcode "You".

- Monster targeting fixed to actually consider every player (Session 46,
  2026-09-17): `monster3d.gd`'s entire AI ran off one `player` reference set
  once via `TargetFrame.local_player()` — fine for a HUD script wanting "my
  own player," but monster AI only ever runs on the server, where "the local
  player" IS the host's own character. A monster could never notice or
  attack any other connected player at all — this was THE reason a second
  test player took zero damage and was never chased. Replaced with
  `_nearest_player()`, re-resolved every frame, scanning every node in the
  "player" group and picking whichever is physically closest; once real
  threat exists, `get_current_target()` already correctly overrides this
  with the highest-aggro attacker, so this only governs who gets
  noticed/chased before combat starts.
- Threat relay (found while fixing the above): `add_threat()` was never
  reaching the real server-side monster for a non-host player's damage —
  player3d.gd's own `add_threat()` call only mutates whichever machine is
  running it, which for a non-host attacker is their own throwaway puppet
  copy of the monster, not the authoritative one. Fixed by calling
  `add_threat()` directly inside `apply_networked_damage()` (already runs
  authoritatively on the server for every relayed hit, including pets),
  resolving the attacker's peer id via the existing `_resolve_peer_to_player()`.
  Uses the plain damage amount rather than the attacker's own
  `combat_node.generate_threat()` — `active_effects` (stance threat_mult)
  isn't a replicated field, so the server can't compute that bonus for a
  remote player's combat_node accurately; same trust-the-reported-number
  trade-off the damage amount itself already makes.
- Bleed-out revival (Session 46): another player healing (a real heal spell)
  or bandaging (right-click a downed ally in the 3D world — see BANDAGES
  below) a bled-out ally now brings them back up if it raises their HP above
  0, before their bleed-out timer expires. `player3d.gd`'s
  `_check_bleedout_revival()` is called from both `apply_networked_heal()`
  (the remote-heal-received path) and `_heal_target()`'s direct-heal branch;
  logs/broadcasts "PlayerName comes back to life!" via the existing combat
  message relay.

NOT yet working / known gaps:
- No server-side re-verification of reported damage (see the trade-off
  above) — not a concern for a trusted-peers private game, would matter for
  a public/competitive one.

DARK SIGHT / IMPROVED DARK SIGHT (replaces the 2026-09-17 "ultravision"; 2026-09-19)
================================================================================
Racial traits in character_options.json (races.<race>.traits): `improved_dark_sight`
(Dwarf, Gnome, Troll, Dark Elf) and `dark_sight` (Elf, Half-Elf, Halfling, Ogre,
Half-Orc, Lizardkin); Human has neither (it gets `torch_burn_bonus` 0.5 instead).
Text shown on character creation comes from the top-level `trait_descriptions`.
DayNightCycle._refresh_dark_sight() reads the LOCAL player's race and sets
dark_sight_strength (1.0 improved, dark_sight_basic_strength = 0.5 for basic). At
night (weight 1 - daylight) and only while `outdoors` is true it floors the sky
colours, raises ambient energy and multiplies moon energy by that strength —
measured screen luminance at night: Human 0.086, Dark Sight 0.164, Improved 0.252,
noon identical. Each client renders its own lighting, so it is inherently
per-viewer. The earlier version (a per-camera Environment override in
camera_controller.gd driven by a hardcoded race list in player3d.gd) was REMOVED:
it could not do tiers, was fed from a list instead of the data, and would have
stacked on top of this. A zone with no DayNightCycle, or outdoors = false, gives no
benefit ("Deep Darkness").


MULTI-BOLT SPELLS (added 2026-09-18, Session 47)
================================================================================
Data-driven alternative to hardcoding a per-spell case for a "fires N bolts"
spell — `player3d.gd`'s `_resolve_spell_cast()` checks a spell's `bolt_count`
field (default 1) right where the "enemy" branch would otherwise compute a
single hit, and if >1, hands off to `_cast_multi_bolt_spell()` instead:
fires that many separate damage instances at the one target, each with its
own `_compute_spell_damage()` resist roll, combat log line, threat
generation, and relay — stops immediately if the target dies mid-volley. An
optional `extra_bolt_chance` field (0.0-1.0) adds a chance at one more bolt
beyond `bolt_count`, for spells like Unstable Missile/Chaos Barrage whose own
description promises it. Currently used by Magic Missile (3×6), Arcane
Barrage (3×50), Unstable Missile (3×30, 10% extra), Chaos Barrage (4×40, 15%
extra) — all four originally had `damage` set to the bolt COUNT instead of
the per-bolt amount (an authoring mix-up, not a game bug) before this. Any
future multi-hit spell just needs the two data fields, no new code.

`pet_minion.gd`'s `cmd_attack/follow/sit/guard/assist/dismiss()` each call an
overridable `_phrase_*()` function (`_phrase_attack(target_desc)`,
`_phrase_follow()`, `_phrase_sit()`, `_phrase_guard()`, `_phrase_assist()`,
`_phrase_dismiss()`) instead of hardcoding a `_say()` line inline — same
override pattern `_pet_title()`/`_pick_random_name()` already used. Base

`phantasmal_echo_pet.gd` (Spiritweaver) and `wildspeaker_pet.gd`

Any new pet subclass should override these too.


SHADOWBLADE — Backstab / Shadowstep / Stealth stance (added 2026-09-18, Session 47)
================================================================================
Closes the last documented class-parity gap (see [[project_class_rollout]]) —
all 13 classes now have real, working mechanics.
- **Stealth** is a real Stance now (`class_stances.json`'s new `Shadowblade`
  entry, `stealthed: 1.0` modifier), toggled on the stance bar exactly like
  the tank stances (`stance_bar.gd` needed zero changes — it was already
  fully generic). Nothing previously ever set the `stealthed` modifier at
  all, so this is also what makes Backstab's stealth condition reachable.
- **Backstab** (`player3d.gd`'s `_resolve_spell_cast()`, hardcoded case
  right where multi-bolt spells are checked) now requires the caster be
  behind the target — dot product of the target's facing vector against the
  direction to the caster, `> -0.5` rejects (roughly a 120° rear arc counts
  as "behind") — UNLESS `combat_node.is_stealthed()` or
  `is_currently_invisible()`, matching the spell's own "from stealth/behind
  target" description (either condition, not both required).
- **Shadowstep** (a new `"none":` case in the `match spell_target:`
  statement — that target value was never handled at all before this, so
  casting it silently did nothing) teleports the caster 2m behind the
  target (target's raw +Z basis vector — Godot's forward is -Z, so "behind"
  is the un-negated Z axis), faces them at the target afterward
  (`look_at()`, flattened to horizontal), and applies the same
  `"invisibility"`/`{"invisible": 1.0}` effect the pre-existing Invisibility
  spell uses. The nameplate change to "(a shadowy figure)" needed zero new
  code — `TargetFrame.nameplate_name()` already handles any invisible
  entity generically, player or monster.
- Four other classes' teleport spells share Shadowstep's old "does nothing"
  bug and are still unbuilt: Aetherfist's swift_step/wind_dash, Arcanist's
  blink, Chaosborn's chaos_rift (all `target: "none"`) — only Shadowstep was
  requested/built this session.


GENERIC SPELL-EFFECT ENGINE (added 2026-09-17, Session 45)
================================================================================

`player3d.gd`'s `_apply_generic_spell_effect()` (called from every `_resolve_spell_cast()`
target branch's `_:` fallthrough — enemy/self/group/cone/pbaoe/chain) drives real
behavior off a spell's own `effect_type`/`duration`/`damage` fields, for any class,
without per-spell code. Named per-spell special cases (Voidknight/Spiritweaver's
original hand-tuned spells) still take priority and run first.

Effect types handled: `heal`, `hot`/`dot` (via `CombatNode.apply_effect()`'s
`tick_heal`/`tick_dmg` params), `buff`/`debuff` (flat `damage_mult`), `snare`/`root`
(`speed_slow`), `blind` (`hit_chance`), `silence` (a modifier flag only — no monster
casting exists yet to consult it), `absorb` (flat damage-absorption pool, self-target
only in current data), `cure` (removes the first active effect whose *originating
spell* was enemy-targeted — see below), and `stun`/`fear`/`charm`/`mesmerize`/
`confuse`.

stun/mesmerize/confuse (and fear as a fallback if `apply_fear()` doesn't exist on the
target) all share one placeholder behavior: target can't attack for the duration,
same mechanism as the pre-existing Improved Disarm stagger. Real flee/allegiance-
flip/randomized-action behavior doesn't exist for those three yet. Fear and Charm got
upgraded past this placeholder later in the same session — see their own sections.

Debuff-vs-buff for the buff bar's red highlight (`buff_bar.gd`) is decided by the
spell's `target` field (`enemy` = harmful to whoever it lands on), NOT `effect_type`
or `spell_type` — both of those describe the spell's own mechanical shape/authored
polarity, not whether landing on a given active_effects owner is harmful (e.g. Aura
of the Shadow is `effect_type: debuff` because it debuffs nearby enemies, but is a
self-buff for the caster; dozens of clearly-beneficial group spells are mis-tagged
`spell_type: detrimental` in the source data).

Known data-authoring pattern to watch for when adding new spells: `target`/
`spell_type`/`effect_type` are three separate, sometimes-inconsistent fields.
`target` is the most reliable (load-bearing for actual spell resolution); several
self-buffs have been found mis-tagged `target: enemy` and fixed as they turned up
(`arcane_armor`, `ki_barrier`, `wholeness_of_body`, `unstable_ward`, `wild_barrier`,
`chaos_weave`, `chaos_shield`) — there may be more not yet found.


TRADESKILLS — COOKING / ALCHEMY (added 2026-09-17, Session 45)
================================================================================

New generic `Scripts/tradeskill_window.gd` + `Scenes/tradeskill_window.tscn`,
draggable/resizable/persistent like every other window, shared by every station.
Recipes live in `Data/tradeskill_recipes.json`, keyed by `station_id` — adding a new
station (a stove, a forge) is pure data, no new window/script code needed.

- `Scripts/tradeskill_slot.gd`: one of 4 ingredient slots. Accepts the same drag
  payload shape `slot_button.gd` uses; takes the WHOLE dragged stack (not always 1),
  removing it from the real inventory via `Inventory.consume_amount()` immediately —
  it's a staging slot, not a real inventory slot. Closing the window without crafting
  refunds whatever's staged. Icon uses `texture_normal` (the same property
  `backpack_ui.gd` actually uses) and `tooltip_text` for the hover-name.
- Recipe matching (`_find_best_recipe()`/`_compute_multiplier()`) computes how many
  times a recipe divides evenly into what's staged, so a stack of 4 raw meat against
  a 1-raw-meat recipe crafts all 4 at once — not an exact 1-for-1 requirement.
- Campfire cooking: `campfire.gd` added a `cooking_station` group + `COOK_RANGE`/
  `STATION_ID`/`display_name` — right-click dispatch in `player3d.gd`'s
  `_try_open_shop_or_loot()` is range-based, not raycast (no collision body to hit),
  checked before falling through to corpse-looting.
- Alchemy: new `basic_alchemy_kit` item (right-click → Open, via a new
  `tradeskill_station` item field `slot_button.gd`'s inspect popup checks for).
- A successful craft raises the matching skill (Session 47, 2026-09-18) — was never
  wired up at all before this. `_finish_craft()` calls a new `_tick_tradeskill()`,
  mapping `station_id` straight to a `player_skills.json` crafting skill via a
  `STATION_SKILLS` const (`campfire` → cooking, `basic_alchemy_kit` → alchemy); a new
  station just needs an entry added there.
- New items: `cooked_meat` (food, +25 satiety), `basic_poison` (right-click →
  Apply to Weapon → pick equipped weapon slot if dual-wielding → sets
  `poison_bonus_damage` on that equipped item instance, read in
  `_apply_equipment_from_inventory()`'s weapon-damage calc).


SPELL LEVEL GATING (added 2026-09-17, Session 46)
================================================================================

`cast_spell()` had no level check at all before this — found via a fresh level-1
Troubadour able to cast a level-2 spell. Now checks
`spell.class_level_requirements[player_class]` against `combat_node.level`, falling
back to the spell's flat top-level `level` field only if this class genuinely has no
entry in `class_level_requirements` (shouldn't normally happen). Deliberately not
just the flat field — the same spell can require a different level for different
classes sharing it (e.g. Improved Block is Voidknight:3 but Blademaster:7), and the
flat field only ever reflects one of them.


BARD SONGS — TOGGLE / AUTO-RECAST SYSTEM (added 2026-09-17, Session 46)
================================================================================

The real, implemented Troubadour mechanic — see [[project_class_rollout]] in Claude's
memory for why an earlier design note (delayed-effect-on-deactivation) is wrong/stale.

- Casting a Troubadour spell toggles it on/off rather than one-shot casting. Gated on
  `player_class == "Troubadour"` in `cast_spell()` — applies to any of their spells
  uniformly, not a per-spell data flag. `player3d.gd`'s `_active_songs: Dictionary`
  (spell_name -> true) tracks which are currently "playing."
- While on, `_tick_cooldowns()`'s new `_tick_active_songs()` checks every active song
  every frame and auto-recasts it (`cast_spell(spell_name, true)`, the new
  `is_auto_recast` param) the instant its own `_spell_cooldowns` entry clears. Checked
  every frame rather than edge-triggered on purpose — a transient block (still mid-
  cast-animation from the previous trigger) naturally retries next frame instead of
  getting permanently stuck. `is_auto_recast=true` also suppresses "not ready"/
  "already casting" log spam and skips the toggle-on/off decision itself (so the
  automatic re-trigger never turns the song off).
- A genuine failure during an auto-recast attempt (target died, ran out of mana)
  removes the spell from `_active_songs` and logs why the song stopped, instead of
  retrying forever.
- **REVERSED 2026-09-18 (Session 47), per explicit user correction — only ONE song
  plays at a time now.** The original design let multiple songs stack/auto-recast
  independently forever; the user reported that as a bug ("it appears like it's
  trying to keep two songs running simultaneously... only the last song should stay
  running"). `cast_spell()`'s toggle-on branch now clears every other entry out of
  `_active_songs` before adding the new one (logging "[Song] fades as you begin a new
  song." for each one it replaces) — whatever it replaces isn't ripped away
  instantly, its already-applied buff (`CombatNode.active_effects`) just runs out on
  its own remaining duration, same as a normal toggle-off. Do not re-introduce
  multi-song stacking if asked to revisit this again.
- **All Troubadour "group"-targeted songs are true area-effect now (Session 47)** —
  per user correction: they were only ever landing on ONE ally (defaulting to self),
  despite every song's own description saying "allies in Xm"/"grants party". Gated
  specifically on `player_class == "Troubadour"` in the `"group"` branch of
  `_resolve_spell_cast()` (`_cast_troubadour_group_song()`) — NOT a blanket engine
  change, since `target: "group"` is shared by 150+ single-ally-target spells across
  every other healer/support class (Lightmender's entire kit, Lightsworn,
  Spiritweaver, etc.), which really do mean "cast on whichever one ally you have
  selected." Troubadour's songs now hit the caster plus every non-Enemy within radius
  (default 8m, matching most songs' own description text; tunable per-spell via a new
  `aoe_radius` field for outliers like Master Anthem's stated "affects 15m").
- **`cast_message` spell-data field (Session 47)** — lets a self-cast buff's message
  be edited directly in `player_spells.json` instead of the generic engine's default
  "Target is empowered."-style text (which read as "Yourself is empowered." for a
  self-cast, per a user bug report on Song of Courage). Written in 2nd person (e.g.
  "You feel courageous.") since it's only ever shown to the actual recipient's own
  screen — only applies when `target_desc == "yourself"` inside
  `_apply_generic_spell_effect()`; every other recipient in a multi-target AoE, and
  every broadcast to third-party observers, still uses the existing 3rd-person text
  (2nd person wouldn't make sense describing what happened to someone else).
- Most songs are intentionally mana-free by design (only a few cost mana) —
  `song_of_courage`'s `mana_cost: 0` is correct data, not a bug.
- Charm Melody (a song, `effect_type: charm`) gets a periodic break-early roll while
  charmed — see monster3d.gd's `state_charmed()` `CHARM_BREAK_CHECK_INTERVAL`/
  `CHARM_BREAK_CHANCE` constants (currently 5s / 15%, placeholder values, not
  balanced). Since the song keeps re-casting itself, a broken charm gets
  automatically re-attempted the moment the bard's own cooldown allows — falls
  straight out of the toggle/auto-recast system with no extra code. This break-chance
  currently applies to ANY charm reaching `state_charmed()`, not gated to
  song-sourced charms specifically (Runecaster's Charm/Mass Charm would get it too) —
  simpler and more consistent than tracking provenance; revisit if that's ever
  undesired for a non-song charm source.
