## Commands & Controls Reference

*Living section — update this whenever a command or keybind is added, removed, or rebound.*

### Chat Commands (type in the chat box at the bottom of the log window, or the NPC dialogue box)
Commands work Linux-shell-style: type any unambiguous prefix and it resolves to the
full command (added 2026-09-14, Session 42) — e.g. `/fol` or `/foll` both run `/follow`,
`/loc` runs `/location`, since no other command starts with those letters. If a typed
prefix matches more than one command it prints "Ambiguous command" and lists the
candidates instead of guessing; a typo that matches nothing prints "Unknown command".
- `/location` (or any unique prefix, e.g. `/loc`) — prints your current X/Y/Z position
  to the General log tab. Renamed from the old bare `/loc` command name (2026-09-14) —
  `/loc` still works, it's now just an abbreviation rather than the literal command.
- `/time` — prints the in-game date/day-night phase and real-world time.
- `/hail` — hails the nearest guard NPC in range (same as pressing H).
- `/appraise` — Insight Check on your current target (same as pressing I).
- `/follow [name]` (added 2026-09-14, Session 42) — follow an NPC or player around the
  zone, e.g. `/follow Sergeant Bryn` to tag along on his patrol. With no name, follows
  your current target (Tab/left-click) instead. Typing `/follow` again on whoever you're
  already following stops following them (toggle). Stops automatically if you press any
  movement key (W/S/A/D/Q/E/turn/jump — taking the wheel manually always overrides it),
  or if the target becomes invalid (despawns, etc). Steers using the same self-managed
  `NavigationServer3D.query_path()` approach guard_npc.gd's patrol system uses (Session
  39/41) rather than `NavigationAgent3D`, for the same long-distance-reliability reasons.
  Stops 3m short of the target rather than walking into them. See `player3d.gd`:
  `try_follow()`, `start_following()`, `stop_following()`, `_handle_follow_movement()`.

### Movement
- `W` / `Up` — move forward
- `S` / `Down` — move backward (also cancels Autorun if active)
- `A` / `Left` — turn left
- `D` / `Right` — turn right
- `Q` — strafe left
- `E` — strafe right
- `Shift` — toggle run/walk
- `R` — toggle Autorun (keeps moving forward until toggled off or you press back)
- `Ctrl` — crouch (hold)
- `Space` — jump
- `X` — sit/stand (rest to regen HP/Mana/Stamina faster)

### Camera
- `F12` — toggle free-look mouselook on/off (captures/releases the cursor). Uncapped
  yaw (spins fully around), pitch capped only to avoid flipping past straight up/down.
  Changed 2026-09-13 — was clamped to 180°/90° like a "head turn"; see below.
- Hold Right Mouse Button — "head turn" look, independent of mouselook: capped to a
  realistic 180° left/right, 90° up/down range, doesn't move past that cap, stays where
  you left it on release. Added 2026-09-13. Hides the cursor only while held (changed
  2026-09-14, Session 42, from `MOUSE_MODE_CAPTURED` to `MOUSE_MODE_HIDDEN` — `CAPTURED`
  locks the OS cursor to the window center every frame, so releasing it — including on a
  quick right-click to loot/shop that never even dragged — made the cursor visibly jump
  to screen center. Head-turn's ±90°/±45° cap never needed `CAPTURED`'s unlimited
  relative motion, so `HIDDEN` fixes it with no functional loss).
- Mouse wheel — zoom in/out
- `Home` — cycle camera mode (behind / angled / first-person)
- Both look modes respect the "Invert Look Y" option (Escape → Options), added 2026-09-14.

### Combat / Targeting
- `Tab` — target nearest enemy
- `Ctrl+Tab` — `target_closest` action (bound, not yet wired to a function — known gap)
- `Ctrl+Escape` — clear current target and turn off autoattack
- `` ` `` (Quoteleft/tilde) — toggle autoattack on current target
- Left-click (cursor visible) — target via raycast; also swings if in range
- `melee_attack` action — defined but currently **unbound to any key** (known gap)
- `1`–`9`, `0`, `-`, `=` — action bar slots (cast spell / use skill in that slot)
- Taking damage from a monster automatically switches your target to it (added 2026-09-14) —
  no more losing track of who's actually hitting you mid-fight.

### Interface
- `C` — toggle character sheet
- `B` — toggle backpack
- `K` — toggle abilities book
- `H` — hail nearby guard or vendor NPC. Hailing a guard gives a random flavor line;
  hailing a vendor (e.g. Aldric the Provisioner) now opens their shop window directly
  (changed 2026-09-14, Session 42 — used to just print a greeting line, so you still had
  to right-click precisely on the vendor's model to actually shop).
- `I` — Insight Check (appraise) your current target
- `Escape` — pause menu (also cancels chat typing without sending, if the chat box has focus)
- `Enter` — opens the chat box for typing when nothing else has focus (added 2026-09-13);
  sends the message and returns focus/movement to the game if the chat box is already focused
- Escape → **Options** (added 2026-09-14) — Music/Sound volume sliders, Invert Look Y toggle,
  and a Loot Preferences list (reset an accidentally-marked item's Loot/Ignore/Sell choice
  without needing to re-encounter it). Settings live in `user://settings.json`, separate from
  character saves.
- Every HUD/UI window is now draggable and remembers its position across sessions
  (added 2026-09-14) — previously only the chat window did; player frame and target frame
  had no drag handler at all.

### Looting
- Right-click a corpse (cursor visible) — opens the loot window, or auto-resolves and
  skips the window entirely if every item on the corpse already has a saved preference
- Loot window has Loot / Ignore / Sell toggles per item (added 2026-09-13, rendering fixed
  2026-09-14 — Godot's CheckBox wasn't drawing its check glyph at all, so these are now
  self-styled toggle buttons instead) — toggling one sets a permanent preference for that
  item id (applies immediately to the current drop too) so future drops of it are handled
  automatically without opening the window. Currency always auto-collects, no toggle needed,
  and now logs "You receive X Copper." same as any other pickup (was silent).
- The window auto-resizes to fit its contents (added 2026-09-14).

### Food & Water
- Auto-eat/auto-drink (added 2026-09-14, Session 42) — the moment satiety or thirst
  drops below 25, the player automatically eats/drinks the first matching item found
  in their inventory (basic slots checked first, then bags) — no more manually opening
  the backpack to eat. Falls back to the old "Your stomach growls"/"Your throat is dry"
  warnings if nothing suitable is carried. Manual Eat/Drink from the inventory
  right-click menu still works exactly as before.
- Both manual and automatic eating/drinking now print a random flavor line from
  `Data/food_drink_flavor.json` (e.g. "You consume Iron Rations. Yumm! That was
  tasty!", "You quench your thirst with A Flask of Water. Ahhh! That hit the spot.")
  instead of the old plain "(Hunger: X/100)" message.

### Saving
- Your position is now saved every time the game saves (Save, or Save & Exit from the
  pause menu) and restored on next login, so you log back in exactly where you logged
  out (added 2026-09-14, Session 42) — previously you always woke up at the zone's fixed
  spawn point regardless of where you'd actually been. Separate from your bind point
  (death-respawn location), which is unaffected.

## 2026-09-16 — Session 43: New race/mob/vendor models, attack/cast animation timing fixes

### Attack animation timing (player3d.gd, monster3d.gd)
- Fixed a real cutoff bug: `attack_current_target()`/`perform_melee_attack()` used
  to hold the swing animation for a hardcoded 0.3s before letting movement-based
  animations take back over — but real swing clips run ~2.3-3.8s, so every attack
  was visibly chopped off after a fraction of its length. Both now hold for the
  real clip length instead (`_attack_animation_duration()`).
- Since that hold is now longer than the 1.0s attack cooldown, a new swing can
  legitimately start before the previous swing's hold-timer finishes — added an
  `_attack_generation` counter so an earlier swing's delayed timer can't wrongly
  cut a newer swing's animation short.
- Per user request ("make sure the mobs don't have a much faster attack than the
  player"): `attack_cooldown` itself is now set to the real swing length each
  attack too (previously a flat 1.0s), and `monster3d.gd`'s `perform_attack()`
  got the same treatment (previously a flat 1.5s regardless of animation) so
  humanoid mobs' attack rate stays in line with the player's instead of
  outpacing it.

### `/follow` command (`player3d.gd`, `game_log_window.gd`)

`/follow [name]` — follow an NPC or another player around the zone (e.g.
`/follow Sergeant Bryn` to tag along on his patrol route). See the Chat
Commands reference at the top of this file for full behavior. Implementation:

- `try_follow(query)` resolves a target: empty query uses `current_target`
  (Tab/left-click selection); otherwise searches groups `npc_guard`,
  `npc_vendor`, `monsters`, and `player` by case-insensitive substring match
  on display name (`TargetFrame.display_name()`, with a `player_name`
  check first for future multiplayer), nearest match wins. Calling it again
  on whoever you're already following toggles follow off.
- `_handle_follow_movement()` steers toward the target using
  `NavigationServer3D.query_path()` directly — the same self-managed
  approach `guard_npc.gd`'s patrol system uses (Session 39/41), not
  `NavigationAgent3D`, for the same reason: `NavigationAgent3D`'s cached
  path was found to go stale over long distances / after the target moves
  out from under it. Repaths every 0.75s (`FOLLOW_REPATH_INTERVAL`) rather
  than every frame, drops waypoints as it passes within 1.5m of them
  (`FOLLOW_WAYPOINT_EPSILON`), stops 3m short of the target
  (`FOLLOW_STOP_DISTANCE`) instead of walking into them, and turns via
  `look_at()` toward the next waypoint (Y-flattened so it doesn't pitch).
- Wired into `handle_movement()`: any manual movement input (forward,
  backward, strafe, turn, jump) cancels follow immediately and hands
  control back, same as pressing backward already cancels Autorun.
- Also invalidates cleanly if the target despawns mid-follow
  (`is_instance_valid()` check each frame).

### Chat commands are now Linux-style prefix-matched (`game_log_window.gd`)

`_resolve_command()` added: given a typed command, matches it against a
`COMMANDS` list of canonical names — exact match wins immediately, else any
*unambiguous* prefix resolves (e.g. `/fol` → `/follow`), else it prints
"Ambiguous command" with the candidate list, or "Unknown command" if nothing
matches. Renamed the old literal `/loc` command to `/location` as the
canonical name (`/loc` still works, it's just an abbreviation now rather
than the literal command) — the clearest example of the new behavior, and
what prompted doing this generically for every command instead of one-off.

### Food/water auto-consume + flavor text (`player3d.gd`, `Scripts/inventory_autoload.gd`, `Data/food_drink_flavor.json`)

- `Inventory.find_first_by_restores(restores)` — new helper, searches basic
  inventory slots then bags for the first item whose def has a matching
  `restores` ("satiety"/"thirst"), returning the same
  `(slot_type, slot_index, bag_slot, item_index)` addressing
  `Inventory.consume_one()` already expects.
- `player3d.gd`'s `update_vitals_decay()`: the moment satiety/thirst ticks
  below 25 (the existing "low" warning threshold), `_try_auto_consume()`
  now fires first — eats/drinks a matching item if one's carried, which
  naturally suppresses the low/empty warning messages that follow in the
  same tick since the vital is back up. No item carried → same warnings as
  before, unchanged.
- New `Data/food_drink_flavor.json` (`eat`/`drink` line pools, `%s` for the
  item name), loaded via the existing `NPCFlavorText` helper class (same
  reusable picker `player_death_flavor.json`/`guard_flavor_text.json` use).
  `consume_food_or_drink()` (used by both manual Eat/Drink and the new
  auto-consume path) now prints a random line from it, e.g. "You consume
  Iron Rations. Yumm! That was tasty!" / "You quench your thirst with A
  Flask of Water. Ahhh! That hit the spot." — replaces the old plain
  "You eat X. (Hunger: N/100)" message.

### Player position saved/restored across sessions (`Global.gd`, `player3d.gd`)

- `Global.save_player_data_to_file()` now captures the live player's
  `global_position` into `player_data["last_position"]` right before
  writing — done centrally here rather than patching every one of the
  several call sites (pause menu Save/Save & Exit, bind point setup, etc.)
  individually, so it can never be forgotten at a new call site later.
- `player3d.gd`'s new `_restore_last_position()` runs in `_ready()` (after
  `load_player_data_from_global()`, before `_ensure_bind_point()`): sets

  for a brand-new character (nothing saved yet), which just keeps the
  zone's default spawn transform. Distinct from `bind_point`
  (death-respawn location, set once on first spawn and otherwise only
  changed by a future bind spell/NPC) — logging out and dying restore to
  different places, same as EQ.

## 2026-09-14 — Session 41: Guard patrol — local obstacle steering, faster aggro scan

Reported after further testing: Bryn got stuck again, this time at the
wagon crash site (unrelated geometry to the gate fixed in Session 39 —
confirms the issue isn't one bad spot, it's that global pathfinding alone
doesn't reliably route around every piece of debris/prop collision on a
long cross-map route); and separately, he "walked through a group of
enemies and only engaged the one he ran into directly."

### Local obstacle steering (`guard_npc.gd`)

- New `_steer_around_obstacles(direction)`, called from `_move_toward()`
  right before committing to a movement direction: casts a short forward
  ray (`OBSTACLE_CHECK_DISTANCE`, 1.5m) along the intended heading; if
  clear, uses it unchanged; if something's directly ahead, tries a series
  of alternate headings (`OBSTACLE_AVOID_ANGLES_DEG`: ±30°, ±60°, ±90°,
  widening outward) and walks the first one that's actually clear instead.
  A real-time local sidestep layered on top of the global path-following
  system rewritten last session — rather than continuing to hand-fix
  individual navmesh trouble spots one at a time as they turn up (the gate,
  now the wagon crash site, potentially more elsewhere on a ~4000-unit
  route), this handles "something's in the way right now" generically,
  independent of whether the baked navmesh accounts for that particular
  piece of geometry. The existing stuck-detector (Session 39) remains the
  fallback for anything this can't steer around.
- Verified headlessly: a direction with nothing ahead passes through
  unchanged; a real `StaticBody3D` wall placed directly in front produces a
  genuinely different, clear heading instead of driving straight into it.

### Faster aggro scan (`guard_npc.gd`)

- `SCAN_INTERVAL` was `1.0` — at ~3 m/s and a 3m `PATROL_ENGAGE_RANGE`, a
  patrolling guard could cover nearly its entire engage range in the gap
  between two consecutive scans, meaning most of a cluster of monsters
  would simply never be "in range" at the exact instant a check ran. Dropped
  to `0.2` (caps travel between scans to ~0.6m, reliably catching anything
  the engage range actually covers). Stationary guards are unaffected
  beyond reacting slightly sooner.
- Verified headlessly: a cluster of three monsters placed ahead of a moving
  guard's path is now correctly noticed and engaged, where before only
  whichever one he happened to be standing next to at a scan tick would be.

### Combined regression check

Ran the full patrol loop for 2 minutes straight after both changes: steady,
uninterrupted progress the entire time (~15.5 units every 5s, matching his
move speed) covering 343 units total with zero stalls — well past where he
previously got stuck, and no jitter/instability introduced by the new
per-frame steering raycasts.

## 2026-09-14 — Session 39: Guard Bryn's patrol stuck at the gate — NavigationAgent3D going stale over long distance

Reported immediately after Session 38, with a screenshot: Bryn walked
~20m out of the town gate and stopped dead next to a pillar, never resuming.

### Three attempts, in order, before landing on the real fix

1. **First hypothesis (wrong): another instance of the vertical navmesh/
   floor-height bug.** Confirmed via a headless test that
   `nav_agent.get_next_path_position()` was returning a point ~0.72m away
   with the entire difference in Y and zero in X/Z — looked exactly like
   the bug already fixed in `monster3d.gd`, and this file's own
   `path_desired_distance`/`target_desired_distance` were still the
   original, un-fixed `0.5`. Bumped to `1.5` to match. This DID get him
   moving (confirmed: ~17.5 units in 6s) — but only past the very first
   corner. Longer-duration testing showed he stopped again a few meters
   later, and a forward raycast in his direction of travel hit a real wall
   with `normal: (0,0,1)` — `1.5` was loose enough that the agent considered
   itself "arrived" at corners near the gate's tight passage and walked
   straight through a wall corner instead of hugging around it.
2. **Second attempt: a stuck-detector, position-based.** Tightened
   `path_desired_distance`/`target_desired_distance` back down to `0.75`
   (enough margin over the measured 0.72m gap without being as loose as
   1.5) and added logic to detect "hasn't moved in 2s" and snap the Y
   coordinate to the navmesh surface. Extended testing showed this WASN'T
   enough either — he kept re-getting stuck at nearly the identical XZ
   spot, orbiting a few meters for 75+ seconds straight.
3. **Root cause, finally isolated**: a fresh `NavigationServer3D.query_path()`
   called directly from his exact stuck position, every time, consistently
   returned short, sane, obviously-correct corners — but
   `nav_agent.get_next_path_position()` kept offering a corner that led
   right back to the same spot. `NavigationAgent3D`'s own internal path had
   gone stale relative to where he actually was (most likely compounded by
   the earlier stuck-detector attempts externally repositioning him without
   the agent noticing) — the underlying "trust the agent to track its own
   progress along a path this long, then let it recompute on its own
   schedule" approach was fragile regardless.

### The actual fix (`guard_npc.gd`)

Rewrote `_move_toward()` to manage its own corner list
(`_current_path: Array[Vector3]`) via direct
`NavigationServer3D.query_path()` calls instead of relying on
`NavigationAgent3D.target_position`/`get_next_path_position()` at all — the
agent node stays in the scene (still configured, harmless) but is no
longer used for path-following decisions. The path is recomputed
(`_recompute_path()`) whenever it's empty, the target has moved
significantly, or the stuck-detector requests one; corner advancement
(`CORNER_ARRIVAL`, 0.75) is tracked entirely in guard-owned state, so an
externally-moved position (combat interrupting patrol, the stuck-detector,
anything else) can never leave a dangling reference to the agent's own
notion of "where am I on this path." The stuck-detector now just clears
`_current_path` to force a fresh query rather than trying to manually
nudge a position — simpler, and doesn't need to guess how far to move.
Also clears `_current_path` explicitly whenever combat ends and a
patrolling guard returns to `PATROL`, since fighting can move a guard well
off whatever path was cached before the fight started.

Verified headlessly: Bryn now covers real, continuous ground — 308 units
over 100 seconds with steady, unbroken progress the whole way, cleanly
through the exact gate passage that stopped him before. Re-verified combat
interrupting and resuming patrol still works correctly (engage on a nearby
monster, kill it, patrol resumes and moves normally afterward), and
stationary guards (Corwin/Reyna) are unaffected.

## 2026-09-14 — Session 33: Player death/respawn system, monster death lines, and a serious double-damage bug fix

Prompted by: "I went out and found the bandit camp, and they swiftly kicked
my ass!" — an EQ-style death flow was requested: incapacitate at 0 HP
(EXISTING and existing HP=0 previously just froze the player forever, no
recovery), bleed out ~20 more "HP" over time, then true death → respawn at a
bind point, with monsters resetting and walking home rather than farming a
downed player. Investigating "swiftly kicked my ass" surfaced something far
more consequential than expected.

### Bug fix: monster attacks against the player were dealing EXACTLY DOUBLE damage

Root cause, `monster3d.gd`'s `perform_attack()`: `CombatNode.resolve_attack()`
already applies a hit's damage directly (`target.current_hp -= damage`,
`combatnode.gd`) as part of resolving it — but `perform_attack()` then ALSO
called `target.take_damage(result["damage"], self)` for the same hit when
the target was the player, and `player3d.gd`'s `take_damage()` applies
`combat_node.take_damage(amount)` on top of that. Every monster hit against
the player was landing twice. Player-vs-monster, guard-vs-monster, and
pet-vs-monster attacks were all already correct (none of those call sites
had the redundant second application) — this was isolated to monster-vs-player,
which is exactly the direction that made the bandit camp brutal.
- Verified with a headless test before touching anything: a bandit hitting
  the player for a raw, `resolve_attack()`-reported 18 or 47 damage was
  landing as 36 or 94 through the full `perform_attack()` call — exactly
  double, every time.
- Fixed by removing the redundant `take_damage()`/`apply_damage()` calls
  from that branch entirely and adding `player3d.gd::on_combat_node_hit()` —
  handles ONLY the side effects `resolve_attack()` doesn't (auto-target-switch
  to the attacker, the incapacitation check) without re-applying damage.
  Applied the same fix to the parallel (currently unreachable, but
  structurally identical) case of a monster hitting some other
  `CombatNode`-carrying target — added an explicit death check there too,
  since removing the old `apply_damage()` call also removed the death
  check it used to carry internally.
- Re-verified after the fix: the same bandit now lands for exactly 18/47,
  matching `resolve_attack()`'s own reported damage 1:1.

### Player death / incapacitation / respawn (`player3d.gd`)

- `dying: bool` already existed (froze movement/regen via existing gates in
  `_physics_process()`/`_process()`) but nothing ever set it back to false —
  hitting 0 HP was a permanent, unrecoverable freeze. Kept `dying` as that
  same "can't act" gate, layered a real state machine on top:
  **incapacitated** (0 HP, `is_incapacitated=true`, `dying=true`) → 20
  seconds of passive bleed-out (`BLEED_OUT_DURATION`, periodic "You are
  bleeding out..." reminders every 5s) → **true death** → a black respawn
  screen for `RESPAWN_DELAY` (3s) → teleport to bind point at full HP/mana/
  stamina, `dying` cleared.
- The bleed-out window is deliberately passive/deterministic, not more
  combat damage — monsters disengage the instant incapacitation starts (see
  below), so nothing can interrupt or accelerate it. Regen is also frozen
  throughout (the existing `dying` gate already did this), so there's no
  chance of self-stabilizing mid-bleed-out.
- A single overkill hit can drop `combat_node.current_hp` well below 0
  (`resolve_attack()` doesn't clamp) — `die()` clamps it back to exactly 0
  on entry so the HP bar and the bleed-out window both start clean
  regardless of how large the killing blow was.
- Sequence at true death, refined through two rounds of feedback (an EQ1
  reference — red "you have been slain" text, a random flavor line, then a
  black "LOADING, PLEASE WAIT" screen — then "don't copy those messages
  exactly, have something similar"): a red `"You have been defeated by
  <attacker>!"` combat-log line (attacker captured at the moment of
  incapacitation, not true death, since the killing blow's source is what
  actually matters — `_last_attacker_desc`), a random line from a new
  `Data/player_death_flavor.json` (own wording — "Darkness folds in around
  you.", "Your legs give out beneath you.", etc., not EQ's actual text),
  then a full-screen black `CanvasLayer` reading "RETURNING TO YOUR BIND
  POINT..." (own wording, not "LOADING, PLEASE WAIT") held for
  `RESPAWN_DELAY` before the teleport.
- **Bind point**: no bind spell/NPC exists yet, so
  `_ensure_bind_point()` defaults it to wherever the character first spawns
  into the world, stored as `Global.player_data["bind_point"]` (a plain
  `[x,y,z]` array — `Vector3` isn't JSON-serializable), persisted once and
  read back by `get_bind_point()`. Structured so a real bind
  spell/NPC can just overwrite that same field later without touching
  anything else.
- Verified headlessly end-to-end: forcing the bleed-out timer past
  `BLEED_OUT_DURATION` while the player stood far from their bind point
  correctly fired the "defeated by" message, held the black screen, then
  teleported back to the bind point at full HP with `dying`/
  `is_incapacitated` both cleared.

### Monsters disengage and go home instead of farming a downed player (`monster3d.gd`)

- New `force_disengage()`: clears `aggro_table` and, if currently
  `CHASE`/`ATTACK`, switches to `PATROL` with `patrol_target` set straight

## 2026-09-14 — Session 30: Loot silently vanishing, guard chatter range, zoom-to-first-person

Reported while testing a fresh character: looted "Bone Shield" logged as
received but never appeared anywhere in inventory. Also asked for guard/NPC
speech to only show in the log when the player's close enough to hear it
(~5m), and for zooming the camera all the way in to drop into first-person.

### Bug: loot could report success while silently failing to fit

**Root cause, `Scripts/inventory_autoload.gd`**: every "player receives an
item" call site (`corpse_loot_window.gd`'s Take/Loot All/preference
checkboxes, the manual loot-window drag-to-inventory path in
`slot_button.gd`, `monster3d.gd`'s auto-loot, `shop_window.gd`'s Buy) called
`Inventory.add_to_basic_inventory(item_id)` and then unconditionally logged
"You receive X" — the function's boolean return value (false when all 12
`basic_inventory` slots are full) was never checked at any of those sites.
A new character starts with `small_bag` + 6 pieces of unequipped starting
gear already occupying 7 of those 12 slots directly (not in a bag — they're
a staging area to be dragged onto equipment slots), so it doesn't take much
looting before `add_to_basic_inventory` starts silently failing while the
log keeps claiming success.
- A second, independent bug in the same code path: **every** call to
  `add_to_basic_inventory()`/`add_to_bag()` across the whole codebase passed
  no quantity argument, so `create_item_instance(item_id)` always defaulted
  to quantity 1 — a "3x Spider Silk" drop's log message correctly said
  "x3," but only 1 was ever actually added.
- Fixed both by adding a new `Inventory.add_item(item_id, quantity)` —
  merges onto an existing stack in any bag first (correctly applying
  `quantity`), then any bag with room (keeps loot from eating the scarce 12
  `basic_inventory` slots one-per-item when a bag has space), and only falls
  back to a bare `basic_inventory` slot if every bag is full. Returns false
  only when there is truly no room anywhere. `add_to_basic_inventory()`/
  `add_to_bag()` both gained an optional `quantity` parameter (default 1,
  so every existing call site is unaffected) so `add_item()` can thread a
  real quantity through instead of hardcoding 1.
- Every "player receives an item" call site now checks `add_item()`'s return
  value: `corpse_loot_window.gd`'s `_apply_drop()` now returns bool and only
  logs "You receive X" on success, logging "Your inventory is full — you
  leave X behind" otherwise; `_take()`/`_loot_all()`/the preference
  checkboxes only remove the drop from the corpse (`pending_loot`) when it
  was actually applied, so a full-inventory drop stays lootable instead of
  vanishing. Same fix applied to `monster3d.gd`'s auto-loot (falls back to
  the manual loot window instead of disappearing), `slot_button.gd`'s
  drag-to-inventory loot path, and `shop_window.gd`'s Buy.
- Verified headlessly: stacking 3 then 2 more of a stackable item onto the
  same bag slot correctly reaches quantity 5; filling a 4-slot bag correctly
  spills the next item into `basic_inventory`; filling every slot
  everywhere makes `add_item()` return false and `_apply_drop()` leaves the
  drop in `pending_loot` rather than discarding it.

### Guard/NPC speech now range-gated (`guard_npc.gd`)

- `say()` (the single chokepoint both `_say_flavor()`'s hail/engage lines
  and `npc_scripted_conversation.gd`'s day/night scripted guard exchange
  route through) previously logged unconditionally regardless of the

### Camera: zooming all the way in drops into first-person (`camera_controller.gd`)

### Satiety / Thirst — was decaying but non-functional, now a full loop

`player3d.gd` already had satiety/thirst decaying over real time (satiety:
100 real minutes to fully drain from 100; thirst ~50, roughly twice as fast)
and a `get_stat_penalty()` combat debuff below 25 — but nothing could ever
raise them back up (no eat/drink action existed anywhere), the "out of X"
behavior was a flat 20% regen reduction rather than a hard stop, running out
dealt small chip damage instead, and the two `print()` warnings never
actually reached the player (console-only, no GameLog call).

- **Hard regen gating**: satiety <= 0 now halts HP regen (`_process()`'s regen

- **Consumption**: `consume_food_or_drink(item)` (player3d.gd) reads an

  right-click inspect popup (`slot_button.gd`, alongside the existing
  Equip/Learn buttons) for any item with `type` "food"/"drink". Consumes
  exactly one unit via a new `Inventory.consume_one()` (decrements a stack's

  addressing scheme `slot_button.gd`'s drag payload already uses).
  `iron_rations`/`water_flask` (`items.json`) already had unused "Restores 15
  Hunger/Thirst" flavor text — wired that exact number up rather than
  inventing a new one. Added two cheaper tiers, `trail_rations` (+8 satiety,
  2cp) and `spring_water` (+8 thirst, 1cp), for vendor variety.
- **Well Fed buff**: re-evaluated every vitals tick (not a fixed timer) —
  `combat_node.apply_effect("well_fed", INF, {hp_regen_bonus:2,
  mana_regen_bonus:2, stamina_regen_bonus:2})` while satiety AND thirst are
  both >= 75, removed the moment either drops below. Reuses the existing
  generic buff/debuff system (`combatnode.gd`'s `active_effects`, same one
  `campfire.gd`'s "Warmth of the Campfire" and stances use) — shows up on the

  feedback to the player" the request asked for. Added its description to
  `buff_bar.gd`'s `ENVIRONMENTAL_EFFECT_DESCRIPTIONS`.
- **HUD**: `player_frame.tscn`/`.gd` gained Food/Water bars (orange/teal)

## 2026-09-14 — Session 28: Monster balance pass — combat math, zone spawn density, loot expansion

Overnight autonomous session, triggered by: "monsters aren't doing much damage... I
can kill them with the siphon life spell and they're not hitting me for the most
part," plus a request to review the zone's spawn density against its area map
(mausoleum → undead, goblin/bandit camps → goblins/bandits, spider den → spiders)
and to compare loot density/variety to EverQuest starting zones ("way too sparse").

### Bug Fixes

**Monster combat stats were flatly zeroed (`monster3d.gd` `_configure_combat_node()`)**
- Every monster's base STR/CON/DEX/INT/WIS/CHA/LUCK was hardcoded to 0, with only
  flat, level-derived `gear_atk`/`gear_ac`/`gear_hp` offsets driving combat — a
  pattern intended to let the JSON's `armor_class`/`max_health` stay authoritative,
  but with an unintended side effect: melee damage (`weapon_damage + STR/2`), hit
  chance (`weapon_skill*2 + STR + DEX/2 + gear_atk`), and ALL magic resistance
  (`CON/2 + WIS/2`) all lost their stat contribution entirely — confirmed every
  monster had exactly 0% arcane/divine resist.
- This is why a single Life Siphon (~70 flat damage) could one-shot a rat (20 HP)
  five times over and take a bandit (80 HP) to 12% remaining, fully unresisted,
  while monsters barely hit the player back (e.g. a level-3 bandit: 41% hit chance
  for 6% of player HP per hit).
- Fixed by giving monsters real, level-scaled stats (`stat_scale = 8 + level*3` for
  STR/CON/DEX, flat 5 for the rest) while backing out the JSON's hand-tuned
  `max_health`/`armor_class` via `gear_hp`/`gear_ac` so per-mob HP/AC didn't
  silently inflate on top of already-balanced numbers.
- Verified via a headless before/after comparison script: monster hit chance vs.
  player went from 9–41% to 19–55%; damage per hit from 0.6–6.8% to 3.4–10.2% of
  player HP. Life Siphon vs. monsters went from 70–350% (always fully unresisted)
  to 60–65 flat/65–320% of HP with resistances now correctly applying 7–13%.

**Spell resistance had never actually applied, to anyone (`combatnode.gd`)**
- `get_resistance(resist_type)` appends `"_resist"` to its argument itself. Both
  `calculate_spell_damage()` and the (dead/unused, confirmed via grep)
  `calculate_resist_chance()` were calling it with an already-suffixed key
  (`"arcane_resist"`/`"divine_resist"`), producing a lookup for the nonexistent
  `"arcane_resist_resist"`/`"divine_resist_resist"` — always 0.
- This meant spell damage has never been resisted by any target, player or
  monster, in the entire game, until this fix. Fixed by passing the unsuffixed
  `"arcane"`/`"divine"` instead.

  the origin) → Mausoleum/Graveyard/2 Small Crypts undead cluster (4 skeleton
  spawns + a mummy + a mirage_phantom, southeast) → 2 Bandit Camps (4 spawns,

## 2026-09-14 — Session 27: The real monster-movement fix, guard's own animations, humanoid mobs, options menu

### Bug Fixes

**Monsters still didn't chase, even after Session 26's fixes — the actual root
cause** (`monster3d.gd`, `mob_spawner3d.gd`, `Scenes/lumora_outskirts3d.tscn`)
- Session 26 fixed two real bugs (add_threat() not forcing CHASE, and a too-
  short leash) but they weren't sufficient — a monster still stood
  completely frozen even under direct, sustained melee attack. Root-caused

  what let the Session 26 fix look "confirmed" when it wasn't): the zone's
  baked `NavigationMesh` had **zero vertices** — never actually baked,
  despite `NavigationRegion3D` being present and enabled. Every path query

  always saw "no path" and did nothing at all — no movement, not even
  gravity. Re-baking directly failed at first too: the default cell_size of
  0.25m is sized for small indoor spaces, and tried to generate an
  impossibly large voxel grid for this ~180×120 unit outdoor zone ("Baking
  interrupted... would likely crash the engine"). Fixed by setting
  `geometry_parsed_geometry_type = STATIC_COLLIDERS` (bakes from the zone's
  own maintained collision shapes instead of GPU mesh data — faster, and
  what the bake warning itself recommended) and `cell_size`/`cell_height` to
  0.5, producing a real 466-vertex/391-polygon mesh, saved as
  `Data/lumora_outskirts_navmesh.tres` and wired into the scene as an
  external resource (replacing the broken empty embedded one).
- Second, deeper bug found once the navmesh was real: `mob_spawner3d.gd`
  hardcodes a flat Y per spawn entry (`lumora_outskirts_spawns.json`) that
  rarely matches the real terrain height at the randomized X/Z offset,
  leaving mobs floating above/below the ground. A floating mob's first path
  waypoint becomes a pure vertical correction (near-zero horizontal delta),
  and `handle_movement()`'s "basically no movement needed" early-return
  treated that as "arrived" — permanently frozen one layer deeper than the
  first bug. Fixed by snapping spawn position onto the navmesh via
  `NavigationServer3D.map_get_closest_point()` before the mob enters the tree.
- Third bug, found from the SAME 8-second trace after the above two were
  fixed: gravity itself was gated behind the identical "close enough, nothing
  to do" check that gated horizontal movement — so a monster whose
  navmesh-projected waypoint differed from its true resting height by more
  than a hair (the baked navmesh surface can legitimately sit above the
  actual collision floor by a bit) could never fall/settle to the height
  that check would consider "arrived": it needed gravity to reach that
  height, but gravity was gated behind reaching it. `handle_movement()`
  restructured so gravity/`move_and_slide()` run unconditionally every PATROL/
  CHASE tick, independent of whether there's horizontal nav movement to do.
- Fourth and final piece, from the SAME trace: even with all three fixed, a
  monster attacked from ~12m away would take one step then freeze again —
  `NavigationAgent3D.get_next_path_position()` doesn't advance to the next
  real waypoint until the agent is within `path_desired_distance` (was 0.5)
  of the current one, using full 3D (including Y) distance — and the
  navmesh-vs-floor height gap (measured up to ~0.7m on this terrain) alone
  already exceeded that, so the agent could wait forever to close a vertical
  gap it was never going to close. Bumped `path_desired_distance`/
  `target_desired_distance` to 1.5. Verified end-to-end with a real spawned
  bandit, hit from 6m, tracked for 8 full seconds of physics: closes
  distance, correctly switches to melee ATTACK on arrival, holds there.
- Also fixed while in here: leash removed entirely per explicit request (see
  New Features below), and monster chase speed doubled (also below) — both
  needed for the fix to actually feel complete once movement itself worked.

**Guard T-posed** (`guard_npc.gd`, `models/guard/guard_animations.res`)
- The FIRST guard-animation library build (this same session, superseded
  before ever reaching the user — see below) mixed two bone-naming
  conventions in one AnimationLibrary: idle/attack tracks pulled from the
  guard's own downloads use "mixamorig_<Bone>" (matching the Paladin model's
  actual skeleton), while walk/death tracks reused from the player's
  downloads use "mixamorig1_<Bone>". A single runtime skeleton-bone rename
  pass can only satisfy one convention, not both — so walk/death animated
  correctly while idle/attack silently found no matching bone and left the
  guard in bind pose (T-pose) whenever idle or mid-swing. Root-caused by
  inspecting the saved .res file's raw track path strings directly rather
  than re-guessing. Fixed at the build step instead of at runtime: walk/death
  tracks now have every track path rewritten from "mixamorig1_" to
  "mixamorig_" (the OPPOSITE direction — matching the guard's own unrenamed
  skeleton) before being saved into the library, so all four animations
  consistently target the guard's actual bone names and the runtime
  skeleton-rename function was removed entirely (no longer needed).

**Day/night transition had a bright flash at the horizon** (`day_night_cycle.gd`)
- At the exact instant phase flips between DAY and NIGHT, the sun/moon's

  rotation/cool-blue color/dim energy vs. the sun's completely different

### Bug Fixes

**Monsters never chased or fought back when attacked — the real bug**
(`monster3d.gd`)
- `add_threat()` recorded damage into `aggro_table` but never changed
  `current_state` — the ONLY thing that ever moved a monster out of
  IDLE/PATROL into CHASE was `can_see_player()`, a pure proximity check
  (capped at `MAX_AGGRO_DISTANCE`=5m, and as tight as ~1.67m for
  `behavior_type=="passive"` mobs — smaller than the default 2m
  `attack_range`, so even point-blank melee against a passive mob could
  fail to register). Landing a hit would damage the monster and add threat,
  but if that same swing didn't also happen to satisfy the separate,
  narrower sight check, the monster just stood there taking hits forever.
  Fixed by having `add_threat()` itself force `change_state(State.CHASE)`
  whenever amount > 0 and the monster is currently IDLE or PATROL — being
  attacked now always starts a fight, regardless of the vision-range math.
  (A pure miss still generates 0 threat and won't wake a monster on its
  own — you need to land at least one hit.)

**Chat window could permanently lock out player movement**
(`game_log_window.gd`)
- `chat_input` (the chat `LineEdit`) never released keyboard focus after
  being clicked — not on Enter, not on Escape. `player3d.gd` already
  (correctly) blocks movement while any `LineEdit` has focus, so one click
  into the chat box left you stuck until you clicked it again. Separately,
  `W`/`S` are bound to both `move_forward`/`move_backward` *and* Godot's
  built-in `ui_up`/`ui_down` focus-navigation (checked `project.godot`), and
  a single-line field doesn't consume vertical arrows itself, so those
  keypresses fell through to Godot's default "hand focus to some other
  control" behavior — read by the user as "pressing forward/back moves the
  selected tab." Fixed: `_on_chat_input_submitted()` now calls
  `chat_input.release_focus()` after clearing the text; a new
  `_on_chat_input_gui_input()` handler releases focus on Escape too; and
  `chat_input.focus_neighbor_top`/`focus_neighbor_bottom` are pinned to
  itself so W/S can never hand focus off while genuinely typing.
- Added the flip side while in here: `_unhandled_input()` on
  `game_log_window.gd` now grabs `chat_input` focus on Enter when nothing
  else is focused (so you don't have to click the box first) —
  `set_input_as_handled()`'d so it can't double-fire.

**Mouse cursor could get stuck hidden, or mouselook could get silently
cancelled** (`global.gd`, `camera_controller.gd`, `player3d.gd`,
`corpse_loot_window.gd`, `backpack_ui.gd`, `character_sheet.gd`)
- Mouse-mode state was scattered across 6 files, each independently
  hardcoding `MOUSE_MODE_VISIBLE`/`MOUSE_MODE_CAPTURED` with no shared
  source of truth for "is mouselook actually on." Two concrete bugs:
  `corpse_loot_window.gd` forced the mouse to CAPTURED on close even if
  mouselook was never enabled (hidden mouse after looting); every other
  window (pause menu, character sheet, backpack) forced VISIBLE on close,
  silently cancelling mouselook if it happened to be on. Fixed with a new
  `Global.mouselook_enabled` bool (F12/`camera_controller.gd` is the only
  writer) and `Global.restore_mouse_mode()` — every window still forces
  VISIBLE on open, but all now call `restore_mouse_mode()` on close instead
  of hardcoding a mode.

**Fullscreen resolution / camera distortion** (`project.godot`)
- Was launching windowed at a hardcoded 1280×1024 with `window/stretch/
  aspect="ignore"` (non-uniform stretch — the actual source of the reported
  camera distortion). Now `window/size/mode=3` (borderless fullscreen at
  the OS-reported native resolution, not hardcoded), 1920×1080 design
  base, `stretch/mode="canvas_items"` (keeps the 3D scene rendering at full
  native resolution instead of upscaling a fixed-size buffer),
  `stretch/aspect="keep_height"` (fills widescreen monitors instead of
  letterboxing, no non-uniform stretch).

**Night was pitch black** (`day_night_cycle.gd`)
- `moon_energy` (the sun light repurposed as moonlight at night) was 0.04 —
  about 3% of the daytime peak of 1.3. `night_ambient_energy` was 0.05,
  about 5% of daytime's 1.0. Both raised to 0.25 and 0.18 respectively —
  still a clearly dim, moody night, but no longer unable to make out
  terrain. Local light sources (campfires, torches) remain the dominant
  light source at night by design (see the TIME SYSTEM section in
  game_flow.txt) — this only fixes the ambient/moonlight floor.

**Camera look was one clamped mode, tied to F12** (`camera_controller.gd`)
- F12 mouselook was clamped to ±90°/±45° — fine for a "turn your head"
  feel, wrong for a free-look camera (couldn't even look directly behind

## 2026-08-25 — Session 23: Real threat/aggro system (makes threat_mult work)

### New Features

**Per-monster aggro table** (`monster3d.gd`)
- Session 22 wired `threat_mult` into `CombatNode.generate_threat()`, but
  nothing called `generate_threat()` at all and every monster hardcoded
  "the player" as its only possible attack target — so the stance modifier
  had nowhere to have an effect. Added a real (if intentionally small) aggro
  system to fix that:
  - `Monster.aggro_table: Dictionary` (attacker Node → accumulated threat
    float), `add_threat(attacker, amount)`, `get_current_target()` (returns
    whoever has the highest threat, falling back to the player if the table
    is empty).
  - `state_chase()`/`state_attack()`/`perform_attack()` now chase/attack
    `get_current_target()` instead of the hardcoded `player` reference.
    Initial engagement is unchanged — `can_see_player()`'s proximity check
    still decides whether a monster notices the player and starts fighting
    at all; the aggro table only decides *who* it keeps attacking once
    already in combat, which is exactly the decision `threat_mult` needed to
    influence.
  - Aggro table clears when a monster leashes back out of combat (loses the
    fight entirely), so old threat doesn't linger into the next encounter.
  - `perform_attack()` now handles hitting a non-player target: reuses the
    existing `CombatLogFormatter.monster_attack()` "hits you" messages only
    when the target actually is the player, and a new
    `_log_attack_on_other()` for third-person messages ("Skeleton hits
    Skeleton Warrior for 12 damage!") when it isn't.
- Threat is generated (and added to the target's `aggro_table`) at every
  place the player or pet deals damage or heals: `player3d.gd`'s
  `attack_current_target()` and `cast_spell()`'s enemy-damage branch
  (including a healing-threat bump for `life_siphon`'s self-heal, so Necrotic
  Bastion's "+25% Life Drain healing, maintains threat through healing"
  actually keeps the Voidknight on top of the aggro table), and
  `pet_minion.gd`'s `_perform_attack()`. Guards are deliberately excluded —
  monsters still can't target them at all (unchanged from Session 22's
  one-directional guard combat), so they never appear in any aggro table.
- Net effect: if a Voidknight in Shadow Ascendant (-35% threat) fights
  alongside their Morthan's Call pet, the pet generates relatively more
  threat and monsters will actually turn and attack it instead — matching
  the stance's "DPS/solo, not recommended for group tanking" design intent.
  Necrotic Bastion's healing-boosted threat has the opposite effect, keeping
  aggro on the Voidknight as intended for tanking.
- Verified with a standalone algorithm test (aggro-table max-threat selection
  logic + the real `CombatNode.generate_threat()`/`threat_mult` path) since
  `monster3d.gd` can't be loaded in isolation outside the full game (it
  references the `GameLog` autoload, unavailable to a bare headless test
  script) — the full-project `--check-only` pass confirms it compiles
  correctly in the real game.

## 2026-08-23 — Session 20: 3D level collision rebuild, chat/log overhaul, campfire audio, camera clamps, autorun

### Bug Fixes

**3D level collision regenerated from the new Blender export (Scenes/lumora_outskirts3d.tscn)**
- The zone's wall/floor collision was three hand-baked ConcavePolygonShape3D shapes
  frozen from the old 9.5KB placeholder geometry — completely decoupled from the
  actual level mesh, and totally stale after the Blender level art pass (glb grew
  to 112MB+). Built a headless Godot pipeline (`godot --headless --script ...`) that
  walks every MeshInstance3D in the imported .glb, generates a trimesh
  StaticBody3D/CollisionShape3D per mesh with the mesh's true world transform baked
  in, and text-splices the result into the .tscn without touching anything else
  (UIDs, unrelated nodes) — safer than a full PackedScene resave, which was tried
  first and silently dropped resource UIDs and failed to persist edits inside the
  instanced sub-scene at all.
- Re-run twice more as the source Blender file changed (texture size pass, then the
  Floor scale fix below) — collision now regenerates cleanly any time the .glb is
  re-exported.

**Root cause of "character falls through the world" / broken camera / "missing" sand texture**
- All three symptoms traced to one cause: Blender's `Floor` object had its scale on
  Blender's Z axis (which maps to Godot's Y/up axis on glTF export) set to exactly 0.
  Invisible in Blender since the mesh's local vertices already sit at Y=0, but it
  made the object's transform matrix singular. Godot's physics engine threw
  `Condition "det == 0"` trying to invert it every physics tick, corrupting the
  contact normal, which corrupted the player's CharacterBody3D transform — freezing
  movement and breaking the camera (parented to the corrupted transform), which read
  as "nothing is rendering right," not a texture problem.
- Fixed at the Blender source: `Floor` scale Z 0→1. Also caught and reverted a
  `location.z` of 1.0 left over from a first fix attempt (that axis maps to Godot Y
  and was floating the floor 1m above its correct height) back to 0.
- Diagnosed by inspecting the live working .blend directly with
  `blender --background --python` (found via `find -newer`, since the copy tracked
  in `zones/` was stale — the real source lives in a separate working folder) rather
  than guessing from the exported geometry.

**Duplicate "Docks" object removed from the Blender source** — collision mesh count
went from 15 to 14; confirmed intentional, not an accidental deletion.

**Campfire ambient sound not looping (Assets/…campfire…mp3.import)**
- `AudioStreamPlayer3D` (autoplay, max_distance=10.0 for the ~10m audible range) was
  already wired up correctly, but the imported MP3 had `loop=false` — it played once
  on scene load and then went silent forever, even if you walked back into range.
  Fixed: `loop=true`.

### Root Cause
.godot/uid_cache.bin contained stale UID entries for scripts that had been deleted
from the Scripts/ directory (backpack_ui-OLD.gd, character_creation-OLD.gd,
inventory-OLD.gd). Godot tried to resolve these UIDs on startup and failed.

### Fix
Deleted stale cache files and let Godot rebuild them on next launch:
  - .godot/uid_cache.bin
  - .godot/global_script_class_cache.cfg

### Also
Committed archive-2d/ directory to git as a versioned backup of deprecated 2D
scripts and scenes (combatnode-OLD, mob-OLD, player-OLD, backpack_ui-OLD, etc.).
